## 2. Recommended relations and alternatives

Recommend **three new normalized relations and two nullable origin columns**, with existing directory input IDs retained. This is smaller than adding a polymorphic provenance ledger or duplicating an origin edge on every existing directory membership. It also permits a manually selected source snapshot without inventing a model task or a generation fingerprint.

### A. `source_context`

An immutable frozen source-selection snapshot, distinct from output text or physical location:

|Field|Type/nullability|Meaning|
|---|---|---|
|id|UUID PK|Server allocated immutable context identity|
|meeting_id|UUID NOT NULL FK meeting|Owning meeting|
|origin_kind|ASCII code NOT NULL|GENERATION_INPUT or MANUAL_SELECTION|
|generation_input_id|UUID NULL FK generation_input, UNIQUE|Exactly one context for a new generation input; NULL only for manual source selection|
|transcript_confirmation_id|UUID NOT NULL FK transcript_confirmation|Exact confirmed source revision, even when this context is used only for materials|
|material_snapshot_id|UUID NULL FK material_snapshot|NULL is explicit EMPTY; nonnull is exact PINNED snapshot|
|catalog_version|version string NOT NULL|Immutable CATALOG archive identity|
|catalog_sha256|lowercase SHA256 NOT NULL|Exact raw archive SHA, not a business fingerprint|
|created_at|UTC DATETIME(6) NOT NULL|Frozen server creation time|

CHECK: `(origin_kind='GENERATION_INPUT' AND generation_input_id IS NOT NULL) OR (origin_kind='MANUAL_SELECTION' AND generation_input_id IS NULL)`. Hash syntax CHECK. Index `(meeting_id,id)` for authoritative membership/cleanup; unique `generation_input_id` permits multiple NULL manual contexts. Every FK RESTRICT. Source context is append-only; it is not an access token, parser cache, generic JSON archive, or substitute for input config closure.

For GENERATION_INPUT, confirmation/material/catalog must equal that exact input's frozen manifest and config roots. There is exactly one context even for EMPTY materials, created atomically with the input before enqueue. Input ID can be allocated before hashing: generation manifest includes the context's raw fields and selections but **not its own generation fingerprint**. Therefore no hash self-reference. Input-set inherited contexts are already-persisted graph ancestors and verified recursively with a cumulative graph budget/cycle detection.

For MANUAL_SELECTION, there is no generation input, task, fake READY row or fingerprint. D03 freezes an authorized exact confirmed transcript and allowed saved material snapshot with an explicitly archived catalog profile, and its exact parser choices. This represents manual selection of sources, not AI authorship. Source context creation and the new target/evidence are one CAS transaction. Future generation can consume that saved set and its source graph; it does not retroactively attach an input to the manual context.

### B. `source_context_material`

Columns `(context_id UUID, material_revision_id UUID, parsed_document_id UUID)`, all NOT NULL. PK `(context_id,material_revision_id)`; FKs to source_context, material_revision, parsed_document; reverse indexes `(parsed_document_id,context_id)` and `(material_revision_id,context_id)`. This pins exactly one parsed output per material revision within this context; different contexts may choose P1/P2 for the same file and physical locator.

The row list must be a bijection with **all** material_snapshot_item rows of the context, not just materials already cited. Same material revision and parser ID relation, READY state, text file identity/hash and full unit list are application facts checked before commit. Missing selection fails PROVENANCE_UNAVAILABLE; more than one candidate cannot be selected by time/order and fails SOURCE_CONTEXT_AMBIGUOUS until a concrete choice is frozen. A parser retry creates another output; it never changes a previously selected row.

No nullable READY placeholder is introduced. Failed/unsupported parse output may remain in existing parsed_document history, but it cannot participate in a successful material context. The existing product path may retry or explicitly omit failed material using a new applied snapshot. This does not impose a new quota or change approved empty-material behavior.

### C. `parsed_document_profile`

Columns `(document_id UUID PK/FK parsed_document, format ASCII code NOT NULL, parser_config_version version string NOT NULL, parser_config_sha256 SHA256 NOT NULL)`. Format CHECK is PDF/PPT/WORD/TXT. A parser config reverse index supports retained-archive inventory. This append-only one-to-one declaration binds the actual parser output to its archived parser/format semantics. It cannot be inferred from PAGE/PARAGRAPH, a filename, current MIME defaults or a newly installed parser. `parsed_document.parser_version` must exactly equal parser_config_version; the archived raw bytes and SHA must verify.

Keep parsed_document's existing seven columns and existing parsed_unit rows unchanged. A separate typed relation avoids silently changing old parsed-document FullRow hashes and allows legacy absence to mean unavailable instead of guessed format. An existing output with no recoverable format/archive proof remains without this row; never fabricate one from its unit kind.

### D. Direct origin columns on targets and evidence

Add `minutes_element.source_context_id UUID NULL FK source_context` and `evidence_link.source_context_id UUID NULL FK source_context`, each with a reverse index for retention. NULL means legacy/unavailable; there is no default current input and no silent fallback under the new profile. A new element may have zero evidence but still carries its exact selection context (generated or manual), so non-ACTION origins do not depend on suggestion rows. An element's selection context records its inherited source basis, not proof its edited prose was generated by that input.

**Each evidence row's own context is authoritative.** It need not equal the element's inherited context, body input, or action_suggestion.input_id. An ACTION may keep its old raw suggestion while evidence is rebound to a permitted manual/new input context. The target is copied to a new version, new evidence rows carry the new context, and all review credit is recomputed. Body evidence also carries its own context, permitting mixed inherited sources after body edits rather than assuming all evidence came from current body input.

Existing sensitive_detection/background_note input_id already records immutable per-entry generation origin. Resolve their memberships by unique source_context.generation_input_id, then the exact selected material document. Copying their source join rows preserves original input_id. action_suggestion.input_id remains the origin of the unverified suggestion, never the authority for evidence rebinding. No new directory origin column is needed for generated/copy operations or required background prose editing: create a new note/body preserving input_id and all source memberships, which records inherited source basis rather than model authorship. Required operations are detailed below; arbitrary manual multi-origin directory source synthesis is not implied.

Alternatives rejected: (1) evidence.input_id alone fixes some copies but cannot represent an honest manual source selection without a model/task fiction, and leaves parser ambiguity; (2) a generic polymorphic usage table requires weak owner-kind/id links and duplicates existing membership keys; (3) copying every source text/raw model JSON or scanning historical candidates does not create reliable normalized provenance; (4) merely adding format to a locator conflates physical location with parsing usage and still loses P1/P2 contexts.

## 3. Exact membership, identity and catalog rules

Existing physical source_locator identity remains the full typed meeting/file-or-transcript/location projection, with byte-exact nullable section path. Its ID can be reused across G1/P1 and G2/P2. Never create a fake second locator to encode context. Evidence occurrence identity remains evidence_link.id. Directory occurrence identities remain `(detection_id,locator_id)` and `(note_id,locator_id)`. Exclusion identity remains `(revision_id,locator_id,category)`; both sensitive labels survive. Same locator in different memberships remains multiple usages; duplicate keys reject rather than collapse.

Each included EVIDENCE usage resolves its persisted source_context_id. DETECTION/BACKGROUND resolve the parent row's exact input to its unique persisted context. APPLIED EXCLUSION resolves the generation input in which it is applied to that input's unique context. Exclusion represents a physical/category selection, not a claim to remember which of several overlapping detection clicks selected it; this is the already adopted fix1 APPLIED_INPUT meaning. A new input reapplies the physical exclusion against that new context and hashes that new applied context. No exclusion selection-origin backfill or additional click history is fabricated.

Within one context, a locator must resolve uniquely: transcript exact revision/segment in its fixed confirmation; material file/version must belong to exactly one pinned material entry with its selected parser document, and the exact page/paragraph/section must exist. If the same physical full locator would resolve to conflicting material identities within a single catalog, retain the adopted catalog conflict rule and return SOURCE_CONTEXT_AMBIGUOUS; do not select one by list order or silently deduplicate differing versions. This is an ambiguous source identity failure, not permission to remove one material unnoticed. The required mixed G1/G2 case is unambiguous because it has distinct persisted contexts.

The exact catalog property is `bindings:[{format,parser:Ref}]`; a catalog definition is `{contract:"ama.material-catalog.v2",bindings:[Binding]}`. `version` is an arbitrary immutable archive Version (as parser selection is semantic configuration); definitionSchema/contract dispatch fixes the recognized algorithm. Two PDF bindings with parser P1 and parser P2 are legal in the same catalog. EMPTY bindings is valid only when there is no material selection.

Binding identity is `(format,parser.artifactType,parser.version)` with artifactType exactly PARSER_CONFIG. Reject duplicates, same identity with conflicting SHA, or a parser archive whose declared format differs from binding.format. Bindings sort by unsigned UTF8 bytes of format, then unsigned UTF8 parser.version; SHA is never a tie-breaker that permits conflicting identities. Each unique parser Ref has one catalog dependency with exact slot `PARSER_SHA256_` + its 64 lowercase SHA hex digits (78 ASCII characters). Dependency objects themselves sort by their full ASCII slot strings, alongside the exact CANONICAL_CODEC slot. Recompute slot from the validated raw archive SHA; reject missing/extra/duplicate slots or mismatched refs. Slot strings are config-wire tokens, not database CODE values, so they are not silently truncated to64. No version string, URL, command or filename is encoded into a dependency slot.

Each source_context_material selects one exact parsed_document. That document's parsed_document_profile supplies `(format,parser_config_version,parser_config_sha256)` and must match exactly one catalog binding and that archive's full recognized parser definition. There is no default parser by format and no query of all documents followed by newest/first selection. Every selected material document can use a different explicit binding. The complete graph includes all declared catalog dependencies, even if this particular snapshot does not use every supported binding; these are reachable dependencies, not unrelated extra archive roots.

Concrete valid selection: snapshot S contains revisions RA for PDF file FA and RB for PDF file FB. Context C selects `(C,RA,DA)` where DA/profile=(PDF,P1,H1), and `(C,RB,DB)` where DB/profile=(PDF,P2,H2). C's catalog has both sorted bindings and both SHA-named dependency slots. Catalog enumerates all DA and DB units. FA/page1 and FB/page1 remain distinct physical locators; no reparse or latest lookup. A second context C2 may select a new parser output for RA while old C still selects DA. If selection references a parser binding absent from the catalog, fail PROFILE_UNAVAILABLE; missing selection fails PROVENANCE_UNAVAILABLE. Multiple unselected possible documents do not make a persisted exact selection ambiguous; ambiguity exists only while trying to resolve an absent/conflicting selection and cannot be repaired by collection order.

The original same-full-physical-locator conflict rule within a single context remains separate from multiple-parser-per-format support. It is not triggered simply because two PDF files use two parser versions. Parsed-document selection is by exact PK, not `(format,parserVersion)` discovery.

New material parser config definition schema `ama.material-parser.v1`: exact `{contract:"ama.material-parser.v1",format,parserIdentity,unitMapping}`. unitMapping is a finite approved mapping, not executable code. PDF/PPT map PAGE with positive page_no to their distinct page locator kinds. WORD/TXT map PARAGRAPH with positive paragraph_no and exact nullable section_path to their distinct paragraph kinds. A SECTION row can be source-bearing only if this parser's reviewed mapping explicitly maps its positive paragraph_no and nonnull section_path to the same format-specific paragraph locator. Unknown/nonmappable/duplicate finite unit fails the whole catalog, never gets silently dropped; parsers that use SECTION only as structural containers must express the usable text as actual mapped paragraph units before READY qualification. ParserIdentity is a safe immutable implementation identity, not a command/URL. Actual extraction, OCR, size and runtime budgets remain separately qualified.

Build complete catalog from saved confirmed segments plus **every finite mapped parsed_unit of every selected parsed_document**, including valid unused units and the exact knowledge-version locator for knowledge materials. Enumerate by fixed confirmed ordinal then canonical typed locator bytes as in old catalog, validate unique physical identity before aliases; physical line gaps are permitted and never replaced by 1..unit_count. Cross-check unit_count and complete actual row collection. An uninstantiated source_locator is not a missing source: allocate/reuse physical locator rows only when evidence/detection/exclusion needs them. Catalog creation must not depend on existing source_locator rows. Knowledge-version source identity binds provider/external ID/external version/content file SHA as well as parser output. PDF/PPT same PAGE and WORD/TXT same PARAGRAPH remain distinct by archived format.

The input is the origin of the inherited source basis, **not a claim that the newly edited text was model-generated**. New body/row IDs enter rowset/final hashes. ## 5a. Domain-specific origins: no current-input fingerprint in its own preimage

The proposal's shorthand “each usage carries generationInputFingerprint” applies to **saved historical input usages**, not to the current input being computed. Exact domain dispatch is:

|Domain|Source graph scope|Generated origin projection|
|---|---|---|
|GENERATION_INPUT v3 current source catalog / own sourceContext|Current context raw row, complete parser selections/profiles, confirmed segment/source catalog and exclusions|No SourceUsage origin is emitted here. Current input ID and context ID are fixed references; its own fingerprint is absent, not NULL/wildcard/zero/placeholder.|
|GENERATION_INPUT v3 PINNED elements.sourceGraph|Only previously saved input-set element evidence and directory memberships; no body evidence and **no applied exclusion usages**, as already specified by adopted fix1|`{kind:"SOURCE_CONTEXT",contextId,originKind,generationInputId,generationInputFingerprint}`. Generated origins must be **already-persisted graph ancestors**, never current input or any descendant. Compare each exact stored fingerprint only after independent verification under that historical input's own profile/fence. Manual origin generation fields are both NULL by its real tagged union.|
|REVIEW_SOURCES v3|Exact saved target's complete evidence membership|Same five fields; all generated inputs are already stored and independently verified. No current-input-draft alternative is accepted.|
|FINAL_SOURCES v3|All frozen body/set evidence, directories and applied exclusion usages|Same five fields; final body's generated context is already stored, so its exact saved input fingerprint is included. Recompute/verify that input first using the generation rule above; no final/review digest is a dependency of the generation digest.|

In GENERATION_INPUT v3, both EMPTY and PINNED exclusion objects add required `appliedContextId` equal to the current sourceContext.row.id. EMPTY keeps its exact empty entry list; PINNED keeps its complete sorted `(locatorId,locator,category,reasonHash)` entries. This is the complete applied-context binding for the generation manifest: raw context row and parser selections are already included at top level. It does not embed a FINAL-style EXCLUSION SourceUsage or a current fingerprint. Exclusions must resolve in this current context's full catalog before computing the digest.

For saved final hashing, construct EXCLUSION usages from each frozen exclusion PK and the final body's exact generated context. Their generationInputFingerprint is the already computed stored digest. Thus the directed dependency is generation raw context/selection/exclusion → generation digest → final exclusion usage/final digest, never a fixed point. Restoring/editing the saved body does not change this chain. An inherited set claiming the in-progress input ID as its origin is a cycle and fails INPUT_INVALID, even if a caller supplies a plausible digest.

Zero-evidence element source_context_id values are explicit context roots of PINNED element/final closure, alongside usage-derived contexts. They never fabricate an EVIDENCE usage. Context closure must equal the union of those roots and the source context of each expected usage; selection rows/profile rows are complete for each reached context. REVIEW_SOURCES includes the reviewed element's basis context as a context root even if its evidence list is empty; SOURCE_SUPPORT cannot become SUPPORTED merely from that basis context.

## 6. Transaction, authority and retention obligations

Common lock order: request idempotency → all active identities/authorization identity locks (including selected actor/owner dependencies) → task_subject → meeting and fixed-order immutable/domain rows → file_object sorted IDs and references → durable_task/attempt/operation/execution → audit → outbox sequence last. Discover complete ID lock set through bounded nonlocking reads first, then reread/verify under the proper locks; changed set causes transaction restart, never late identity/root acquisition. Compose with B03/B05 rather than adding an independent transaction manager or calling external services in callbacks.

SQL proves typed existence, uniqueness and union/null checks, **not** same meeting, correct material-snapshot membership, READY output semantics, complete units/catalog, allowed source version, current source ACL, archive authenticity, semantic support or complete target graph. D01 owns parser/profile/selection validation and source permission ports; B07 S2 owns exact source/input/config recovery and graph completeness; D03 owns source rebinding and fresh review intent; D04 owns copy/restore and CAS; B08/D05 own fixed final membership/authority; D06 owns guarded source reads; B04 owns actual file ledger/routing; D07 owns cleanup. New columns may be NULL only for old/unavailable states; new v3 writes require nonnull contexts.

Worker completion validates root active/not published, expected business version/cancel epoch, task input/fingerprint, attempt/owner/unexpired DB lease, unchanged settings and complete references before atomic candidate/results/task/audit/outbox. Rejected completion executes no effects. Ordinary edits/adopt/restore/exclusion/review/finalization recheck expectedRevision and permissions; advance root/subject and clear current final as prescribed. No network/fencing/model/company/KB call is part of this design validation.

Contexts and parser selections retain source content_file_id, parsed_document.text_file_id, transcript/batch/media files through their existing typed B04 ownership/reference validation. A copied evidence reference may be the only remaining business reachability to an old parser output: it still protects that output and its file reference from cleanup. Do not use only current meeting/material pointers or current parse_state. Current and historical minutes, candidate graphs, directory inputs, reviews and frozen finals are retention roots while authorized history is retained. No automatic TTL/history truncation.

An actual new business file reference is registered under already defined ownership kinds in the same domain transaction before success; this addendum does not add a blob/file attachment kind. File creation durability and historical backend routing remain B04's responsibility. ## 9. Precise schema dispatch and validation boundary

The three relations add 16 columns; the two legacy-compatible nullable columns add 2: proposed total **96 tables / 727 columns**. All new FK actions are RESTRICT. No migration number is assigned. Origin tags in persisted data are exactly `GENERATION_INPUT|MANUAL_SELECTION`; GENERATED is not a valid tag. Historical dependencies are already-persisted graph ancestors, not ordering by created_at, UUID, candidate order or text. Shared ancestors may be memoized after verification; a visiting ancestor signals a cycle. Graph budgets cover the entire closure across recursive inputs and archive dependencies, and exhaustion is an explicit capability error, never truncation.

`ama.material-parser.v1.unitMapping` accepts only `PAGES_V1`, `PARAGRAPHS_V1`, or `PARAGRAPHS_AND_SECTIONS_V1`. Every mapped unit has actual persisted text/file hash. Unknown unit kind/mapping, duplicate mapped physical locator, count mismatch, missing text or an unmapped structural row fails the entire catalog. This is a proposed technical schema, not approved parser/OCR/product capabilities.
