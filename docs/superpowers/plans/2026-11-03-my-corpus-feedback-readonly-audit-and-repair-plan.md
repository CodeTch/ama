## 2. 原型与需求实际要求

### 2.1 本人反馈页

[HTML 2140 行起](/home/tanren/ama/designDocs/智能会议助手1021版.html:2140) 明确合并两种数据：本人提交的语料反馈、本人提交的声纹样本。合并后按提交时间倒序排序。

正常页面顺序为：标题和说明 → 五个状态页签 → 七列表格 → 原型演示说明。原型没有主体顶部的独立提交工具栏，没有在本人页切换管理员审核队列的按钮，也没有把建议值设为打开详情的按钮。

| 项目 | 必须对应的内容 |
| --- | --- |
| 标题 | 我的语料反馈 |
| 说明 | 仅展示本人提交的内容 · 会议内单次修改须经平台管理员审核后才会更新全局企业语料 |
| 页签 | 全部、待审核、已通过、已驳回、需要补充 |
| 计数 | 本人两类记录的完整计数；切换页签不能改成仅统计当前页 |
| 七列 | 类型、原始值、建议值 / 人员、来源会议、提交时间、状态、审核意见 |
| 语料类型色 | `tag navy` |
| 声纹类型色 | `tag blue`，类型文案“声纹样本” |
| 声纹原始值 | 会议匿名说话人 |
| 声纹建议值 | 被命名人员 |
| 审核状态色 | 通过 green、驳回 red、需要补充 amber、待审核 orange |
| 空审核意见 | 等待平台管理员审核 |
| 空态 | 暂无反馈记录；在转写校正中处理实体纠错或命名说话人后可提交反馈 |

原型默认五条记录包括三条语料、两条声纹，计数为全部5、待审核0、已通过3、已驳回1、需要补充1。这是验收覆盖样本，不能复制为真实用户数据，也不能用来要求新账号必须有五条记录。

## 5. 已有能力和根因

### 5.1 可复用能力

- 真实本人列表、服务端状态过滤、完整文字反馈计数、时间倒序和游标分页。
- PENDING、ACCEPTED、REJECTED、NEEDS_MORE四种文字反馈状态。
- 提交补充、审核、撤销审核和不可变历史；文字反馈在“需要补充”后追加说明可回到待审核。
- 幂等、丢响应恢复、并发版本冲突、身份切换隔离。
- 管理员角色服务端重查、审核不授予源会议读取权、显式提交内容脱敏。
- 会议内反馈绑定源修订和片段、撤回记录、受限的已批准语料查询。
- 独立治理声纹的加密特征存储、审核、授权期限和撤销机制。

因此不需要推翻现有反馈模块，也不能因为用户截图是空态就直接认定API完全没接。本人没有提交时显示0是合理状态；补演示数据不能修复真实缺口。

### 5.2 根因一：数据模型没有表达原型

原型的 `type / old / sug / ctx` 被收缩为 `category / comment`。OpenAPI、后端落库、前端严格响应校验同步固化了这种收缩。表格虽然保留七个表头，实际数据无法填满相应语义。仅改Vue模板无法补回未保存的信息。

### 5.3 根因二：两条提交路径和声纹流程没有贯通

```text
列表页手填会议ID → 旧反馈接口 → feedback → 审核状态
纠错弹窗         → 会议反馈接口 → feedback + corpus_feedback_binding → 治理读取
命名后选声纹     → 保存会议命名 → 固定提示未提交审核
治理页本人上传   → governed_voiceprint → 本人声纹登记/审核
```

前两条存储的是通用文字内容；第三条没有申请；第四条是登录者自己登记声纹，与会议负责人为说话人提交不同，缺来源和申请人，不能直接当成原型列表的声纹数据。

### 5.4 根因三：通过局部验证代替完整需求验收

[既有视觉脚本](/home/tanren/ama/tools/dev/feedback_review_cas_integration.mjs:18) 用实际简化反馈生成原型数据，并清空原型声纹；[第31行](/home/tanren/ama/tools/dev/feedback_review_cas_integration.mjs:31) 固定 `type:'文字纠错'`、`old:'—'`、`sug:row.comment`。这种比对可以验证简化投影的渲染，但无法发现被删掉的业务字段和声纹链路。不能据此断言之前整个视觉报告一定通过或失败；能确定的是覆盖范围不足。

## 6. 修复架构与数据约定

推荐“扩展现有语料反馈 + 会议声纹申请 + 服务端统一列表投影”。只改样式无法解决字段缺失；将所有反馈、审核和恢复模块全部重写又会丢失已有可用机制，均不推荐。

以下是实现建议，不是对原型增加业务功能。接口命名可在实现评审中调整，界面字段和行为必须保持本报告第2节。

### 6.1 结构化实体反馈

在现有feedback模型上增加业务类型、原始值、建议值、可选说明；源绑定扩展为能够定位提交时转写的来源。建议使用明确字段：

| 字段 | 含义 |
| --- | --- |
| feedbackType | PERSON_CORRECTION / DEPARTMENT_CORRECTION / PRODUCT_CORRECTION / FINANCIAL_TERM_CORRECTION / PRODUCT_ALIAS / TERM_PRONUNCIATION，分别对应原型六项中文 |
| originalValue / suggestedValue | 用户确认提交的两个独立值，保留原型可编辑语义 |
| note | 可选补充说明，不并入建议值 |
| meetingId / sourceRevisionToken | 源会议及提交时校验令牌 |
| transcriptRevisionId / segmentIds / correctionId | 服务端可验证的转写版本、片段和纠错来源；保留最小必要上下文快照 |
| submittedBy / submittedAt | 服务端身份和时间，不接受客户端冒充 |

源片段快照与用户填写的originalValue区分保存，避免把用户修改后的反馈原值误当成源转写。绑定与创建必须同一事务，源版本冲突时不留下半条反馈。

使用新迁移扩展模型，不编辑已执行的V030/V044/V062。历史记录继续可读；缺字段保持真实缺失，不从任意comment自动猜出原值、建议或六类类型，不自动把旧WORDING全部改成人名或产品纠错。原型中的MTG编号不能用字符串拼接从UUID伪造；没有确定的业务展示编号时保留真实来源标识。

旧幂等回执和未完成请求必须保留解析与重放能力。前端 `feedback.ts` 的精确字段校验、OpenAPI及生成类型需要同步升级，不能只由后端追加字段。

### 6.2 会议声纹申请

新增会议声纹申请实体，建议名称 `meeting_voiceprint_application`，与正式 `governed_voiceprint` 分离。保存申请人、主体身份、姓名快照、会议/转写/说话人/音频片段来源、对应人员授权引用、样本事实、审核状态和历史；审核通过后关联正式特征记录。

- 每个业务对象只有一份权威审核状态；列表读取申请状态，不再额外创建一条可以独立漂移的通用文字反馈。
- 按applicantId归入“我的”，不能按subjectId或姓名归属。负责人为他人提交仍应在负责人的列表中。
- 样本准备成功、授权有效且后端受理后，才能显示“已提交声纹审核”。
- 准备失败、授权不足或无可用音频不生成待审核假记录；会议命名成功仍保留。
- 申请的待审核/已通过/已驳回/需要补充映射到原型四种状态；正式声纹的撤销、过期保留独立语义，不额外添加未经设计的第六个页签。
- 沿用现有加密、权限、幂等及恢复方式；普通用户不能读取或下载特征向量。

此链路应与[说话人严格原型方案](/home/tanren/ama/docs/superpowers/plans/2026-11-03-speaker-naming-strict-prototype-refactor-plan.md:334) 共用一套申请和反馈投影，不能由两项修复各建一套。

### 6.3 统一列表投影

建议新增内部查询组件 `JdbcMyFeedbackOverview`，由 `FeedbackController` 调用，读取实体反馈与会议声纹申请并统一过滤、排序和统计。正常页面继续使用现有summary入口；旧reviewing调用应通过明确的兼容处理迁往治理，不能让本人页混入其他人的数据。

统一返回 `kind、id、feedbackType、originalValue、suggestedValue、meetingId、submittedAt、state、reviewReason、revisionToken`；`kind`区分CORPUS和VOICEPRINT。声纹suggestedValue为人员显示名，originalValue按原型为“会议匿名说话人”。详情和后续操作用kind定位真实资源。

- 两类数据必须先合并排序再分页，不能各取20条后在前端拼接。
- 计数覆盖本人所有两类记录，与列表使用相同可见范围。
- 稳定顺序建议为submittedAt倒序，再以kind及id打破同时间并列。
- 游标绑定用户、筛选条件及排序位置；不能继续假设只有一张feedback表的UUID游标。
- 延迟响应与身份变化处理沿用现有epoch和AbortController机制。

分页控件的具体展示原型未规定，见第8节；必须先解决全量可读取，不能用删除分页造成静默截断。
