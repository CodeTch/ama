## 一、结论和问题范围

当前存在实质性功能缺口，但不是所有发布能力都没有实现。已有真实目录读取、最终确认快照、首次发布任务、结果查询、幂等保护、正式文档读取及治理底层能力。主要问题是这些能力没有完整连接成需求规定的用户流程，部分必要数据根本没有进入接口和持久化模型。

优先修复四类问题：

1. **失败后无法继续：** 所有非空发布记录都导致目录和提交锁定，前端没有连接已有的重试与重选位置接口。
2. **配置不完整且不能按会议持久保存：** 标签缺失；“保存”仅保存标签页恢复记录；目录信息不足以说明实际可见范围和发布权限。
3. **成功后结果不可持续访问：** 发布结果组件在只读会议详情里被隐藏，正式文档、发布尝试和治理入口随之不可见。
4. **正式文档与权限链路未达到设计：** 当前正式文档是简单静态 HTML，缺少原型文档信息区、版本记录和来源入口；知识库查看者、知识空间管理员的角色入口也不完整。

这不是只改 CSS 可以完成的任务。建议在现有正式链路上补齐数据和交互，不整体重写底层发布系统，也不把 demo 的本地状态机搬入生产页面。

## 四、逐项差异及修复落点

### K01 发布标签缺失

**要求：** 需求 6.1、6.3 要求标签用于知识检索，区别于会议分类，格式与数量限制由后端提供。

**现状：** 正式发布模板无标签输入；`validPublicationCommand`、提交 API 的字段白名单和发布 payload 均没有标签字段；也未找到会议级发布配置及标签规则接口。

**修复：** 在原有“发布配置”卡片内补齐需求指定的标签字段，读取服务端规则并保存到会议配置；提交时冻结所用配置版本。前后端同时修改，不能只添加一个不保存的输入框。

### K02 “保存配置”仅保存在当前标签页

**证据：** `PublicationPanel.saveConfiguration` 调用 `destinations.saveSelection()`，成功文案为“发布位置已保存在此标签页”。`usePublicationDestinations.persist` 写入 `publication-destination` journal，仅含账号、会议、provider、library 和 pathIds。

**影响：** 标签页恢复记录可辅助刷新，但不是需求 6.5 的按会议保存/查询配置接口。新会话、新标签页、重新登录等情形不能据此保证恢复。

**修复：** 增加服务端会议级配置读取/保存及配置版本并发校验；本地 journal 只保留未提交修改或恢复线索。保存失败保留输入，不显示已保存。

### K03 有发布记录后无法恢复已提交位置

**证据：** 自动加载目录的条件包含 `!status.value`；目录操作的锁定条件包含 `!!status.value`。`PublicationStatus` 不含提交时路径和完整目的地快照，页面路径仅依赖当前内存选择。

**复现：** 隔离组件分别读取 FAILED、RUNNING、SUCCEEDED 后，路径都为“请选择发布位置”，库列表长度为 0，没有发起目录读取，保存和提交均不可用。

**修复：** 分别维护“可编辑配置”和“当次提交配置快照”。有任务时从服务端恢复提交路径、标签、确认编号和任务，不依赖重新浏览目录；运行中只读展示原配置，不能显示为未选择。

### K04 知识库信息和权限说明不足

**要求：** 需求 6.2、6.3 要求库名称、说明、实际可见范围、发布权限及不可选原因。

**现状：** `DestinationLibrary` 仅有 `id/name/rootFolderId`；组件中的说明位置是空 `<small>`；只显示泛化的“继承知识库权限”，无法说明所选库到底对谁可见。发布后的 `library-context` 虽有说明和路径，也没有补齐发布前这些字段。

**修复：** 由目录提供方返回真实说明、可见范围摘要、是否允许发布及原因。只展示当前账号有权获知的库信息，对可浏览但不可发布的库禁用并说明原因。前端不得推断“全员可见”或假设负责人天然具有库发布权限。

### K05 搜索范围只是已加载的知识库名称

**证据：** `visibleLibraries` 对已加载 `items` 做 `name.includes`；前端目录 API 没有搜索参数；`PublicationDestinationPage.request` 的库列表参数白名单只有 `limit/cursor`。

**影响：** 位于后续页的匹配库搜索不到；按库说明搜索也无效。当前“搜索已加载知识库”文案虽披露范围，仍不足以完成原型搜索能力。

**修复：** 服务端按库名和说明搜索后分页，游标绑定搜索条件；快速输入只采用最后一次响应。搜索只改变候选，不清空有效选择。

### K06 真正的失败重试没有前端入口

**证据：** `usePublication.submit()` 在存在任何 `current.publication` 时拒绝提交；`retry` 只是执行/查回原命令。`createPublicationsApi` 只提供 FINAL_CONFIRM 与 PUBLICATION_SUBMIT 两类发送。

**已有后端：** `PublicationController` 已有 `zero-effect-retries`、`resubmissions`、`local-recoveries`。它们有明确的原执行状态、无副作用证明、版本和权限检查，不是通用 POST 重发。

**修复：** 增加经过服务端重新核验的可恢复动作投影，前端按以下决策接入已有接口：

| 实际状态 | 正确行为 |
|---|---|
| 原提交结果未知、远端 UNKNOWN | 查回原任务和结果，不能新建发布 |
| 明确失败、内容/确认/目的地不变，满足原样重试条件 | 调用原样重试接口，保留同一个 publication |
| 明确失败且需更换位置 | 保存新配置并按受控 resubmission 规则提交 |
| 未成功发布但内容已修改 | 重新最终确认，然后按已验证的重提规则提交 |
| 本地未发送的任务已被正式判定可恢复 | 使用 local-recovery；不能凭前端超时推断从未发送 |
| 远端成功但本地未正确关联，或需人工处理 | 展示处理原因，禁止继续发出文档创建请求 |
| 成功、撤回、废止 | 只读，不开放重试或重发 |

不能仅删除 `!!status` 或放宽按钮条件。这会绕过已有防重复文档的保护。

### K07 失败原因和下一步动作无法充分表达

**现状：** `PublicationStatus` 没有给用户使用的失败原因、失败阶段和具体恢复动作。`allowedActions` 只有查看冻结版、刷新状态、查看尝试。尝试记录仅直接输出 kind/outcome 等技术枚举，缺乏失败原因和操作者信息。

**修复：** 后端输出可公开的失败码、原因、阶段、允许动作及禁止原因。前端转换为需求规定的“重试发布”“重新选择位置”“重新确认”“查询结果”等操作，不让用户判断底层执行枚举。未知结果与明确失败分开展示。

### K08 发布进度与长任务恢复不完整

**证据：** 组件只显示 READY/RUNNING/RECONCILING 等概括状态，未呈现需求 8.1 的业务阶段；轮询只监听 publicationId，最多 30 次，间隔 2 秒。

**影响：** 长任务会在约一分钟加请求耗时后停止自动读取；同一 publication 在重试后进入新执行，也不能仅靠 publicationId 变化启动新一轮跟踪。此项是源码检查结论，本轮未通过实际长发布任务验证。

**修复：** 以 publication、当前任务/执行及终止状态联合跟踪；返回页面、刷新、同一发布的新执行都恢复查询。只有后端真正记录了对应阶段才展示该阶段，无百分比依据时不展示百分比。已受理任务不因离开页面而取消。

### K09 预览使用冻结正文，但信息不完整

**已有：** `openPreview()` 重新读取最终确认，正文来自 `p.final.body`，不是重新调用 AI；标题只读。这是正确基础。

**缺口：** 配置主卡片缺少确认编号；预览未完整展示文档要求的类别、标签、具体可见范围和可解释的来源标记。预览使用单纯标题/正文加信息，而正式文档还额外渲染固定核心要素分类，两者没有统一的正式文档视图模型。

**修复：** 由确认编号和配置版本确定预览内容及元数据。预览、发布产物和正式阅读使用同一份冻结文档模型；正文保留用户保存的完整文本，来源链接根据权限呈现，不以摘要或重新生成文本替换。加载错误要留在原界面并可重试，确认失效明确引导重新确认。

### K10 成功结果组件被父视图隐藏

**证据：** `MinutesWorkspace` 在 published 状态把 `view` 设为 elements，而 `PublicationPanel` 始终有 `v-show="view==='publication'"`。结果卡片、正式文档链接、发布尝试和治理按钮都位于该组件内部。

**实页核对：** 已发布会议存在正式文档 200 响应，但只读详情中 `.publication` 不可见，当前可见页面没有“查看正式文档”链接。成功弹窗使用 Teleport，首次成功时可能显示，但刷新不会重新提供完整结果入口。

**修复：** 保持原型成功后进入只读会议的行为，同时为发布结果/记录提供持久可见的入口；不把结果能力放进永久隐藏的编辑流程区域。状态读取、发布配置和结果展示分开组织即可，不需要另做一套工作台。

### K11 成功结果数据缺失，跳转语义不一致

**要求：** 需求 8.4 规定文档编号、发布版本、发布人、时间、目标路径、可见范围和处理记录；原型最终成功弹窗中的路径链接进入知识库。

**现状：** 结果投影主要是任务状态，缺上述完整摘要；成功弹窗的路径是普通文本，点击的“查看正式文档”指向 API HTML。发布会议正文中的知识库组件另有库链接，说明可复用的能力存在，但两处没有统一。

**修复：** 汇总真实发布、映射、确认和提供方元数据；版本不能拿执行次数或临时值冒充。弹窗使用原型规定的知识库路径入口，结果区同时保留正式文档入口。路径、标题和时间不能来自 demo 常量。

### K12 正式文档详情没有按原型和 P05 完成

**证据：** `PublicationDocumentView.emit` 输出基本 h1/h2/p/pre/ol，没有原型的文档信息侧栏、顶部编号版本状态、确认与发布记录、来源按钮；内容元数据中已有校验过的确认标识，也没有显示。当前浏览器读取 200 后确实呈现为浏览器默认样式的纯 HTML。

**修复：** 按原型 `/doc` 的页面结构提供正式文档阅读界面，使用实际发布快照及结果元数据；补齐确认人/时间、发布版本、来源会议、引用和来源状态。无截止日期的行动项不强行显示“截止日期：未填写”。不在此引入编辑或发布操作。

### K13 来源关系被校验，不等于用户已经可以追溯

**现状：** 后端对 payload hash、确认、来源 manifest 等进行了严格校验；但正式文档没有可操作的原始证据入口和按条目定位的来源标记，用户无法从正式阅读页面完成需求 9.2 的追溯。

**修复：** 用已经冻结的来源关系生成来源索引和定位信息；每次访问单独检查原录音、会议转写或引用文件权限。无权限/文件失效/无法定位要给出实际原因，不能通过复制敏感源内容到文档规避检查。

### K14 知识库文档查看者入口受会议权限额外限制

**证据：** `JdbcPublicationService.officialDocument` 与 `PublicationDocumentRead.capture` 在提供方 DOCUMENT_READ 之前要求会议 READ。当前会议知识库页也是从用户可读会议列表反查成果。

**差异：** 需求把“知识库纪要查看者”与“会议参会人”分开：可按库权限读取正式纪要，不等于可读会议和源材料。现有项目入口不能覆盖只有库权限、没有会议权限的读者。

**修复：** 补齐按正式文档身份和库权限授权的阅读入口，与会议回看入口分离；保留现有会议/源文件权限检查。原会议作用域入口不宜直接粗暴去掉 READ 检查。增加两类读者交叉验证。

### K15 治理角色和记录页与设计不符

**证据：** 前端治理按钮按 owner 判断；`JdbcPublicationGovernance.owner()` 只接受原负责人身份，history 同样按原负责人控制。当前 `/operations` 的功能为声纹、语料、评测、配置，没有需求 P06 的发布与撤回记录页。

**差异：** 需求指定由知识空间管理员按管理范围查询、撤回、废止；负责人身份不应自动替代管理授权。当前底层撤回/废止任务与状态传播已经存在，不能判定为完全未实现。

**修复：** 补齐真实知识空间管理授权及按库范围的记录查询，再把入口接入对应治理页面。普通会议负责人不因 owner 身份获得治理能力，管理员也不能绕过原始证据权限。

**设计边界：** 需求文档模块六目前仅有标题，没有详细页面与权限配置展开；最终运行的 HTML 也提示主要展示负责人功能。P06 的管理员完整界面和授权来源需要补充可执行设计，不能由实现者自行设计管理后台。该缺口不阻塞 P02–P05 中已定义的修复。

### K16 测试主要证明底层机制，缺乏需求验收

**现状：** 现有单元测试覆盖真实 ID、目录切换/分页、权限失效清理、未知结果不重复发送、只读回看、成功弹窗挂载等。demo E2E 则明确要求不调用产品 API，因此不能证明正式发布已完成。

**修复：** 正式验收以真实会议路由为入口，对下节全部场景检查 UI、接口回读及持久结果；原型截图用于展示校验，不能以 demo 截图或只检查按钮文字代替。

## 七、最需要防止的五类回归

1. **重复文档：** UNKNOWN、丢回执、旧页面重试、同 publication 新执行必须遵守已有幂等与无副作用证明规则。由 Task 3/7 覆盖。
2. **位置串用：** 两场会议、两个标签页、同名目录、库切换和目录被删除时，草稿、提交快照及服务端配置不可混用。由 Task 2/4/7 覆盖。
3. **错误版本发布：** 预览后修改正文/基础信息、旧确认、旧标签配置并发覆盖都不能进入新发布任务。由 Task 2/4/5/7 覆盖。
4. **越权或过度拒绝：** 库读者不应被要求拥有全部会议权限；有库权限也不能获得源录音权限；负责人不自动具有治理权限。由 Task 6/7 覆盖。
5. **结果不可达：** 成功弹窗关闭、刷新、直接访问、超过一分钟的任务和同 ID 重试后，用户仍能看到状态、下一步动作与正式结果。由 Task 3/5/7 覆盖。

## 八、实施前仍需补齐的设计信息

这些不是可以由前端自行假设的参数：
