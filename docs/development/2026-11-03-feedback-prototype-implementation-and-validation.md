## 修复过程中实际发现的问题

- 结构化提交重复在会议根锁后获取身份前置锁，导致真实提交 503：调整原子创建与来源校验顺序，并验证来源失败整笔回滚。
- 未分配说话人的真实音频片段缺少命名入口：通过已有命名交互分别展示每段未知身份，不自动合并不同未知人员。
- 开发热更新可能替换应用注入 Symbol，导致上下文丢失：稳定注入键；实操脚本只冻结开发热更新，业务 HTTP、数据库和外部接口保持真实运行。
- 审核生效字段在共享后端加入后与前端严格响应校验不一致：增加有界、明确枚举的兼容校验和契约，非法“成功”状态仍被拒绝。
- 旧反馈进入新统一列表后缺少详情入口：按旧反馈结构字段为空保留原有详情及恢复入口。
- 接受本段纠错时误弹审阅窗口：恢复提示曾将正常请求发送/回读间隙视为待恢复，改为覆盖整个纠错操作期间，只有真实未完成请求进入恢复交互。
- 共享重启出现迁移版本冲突：保留已执行的 V072/V073，未执行的撤回理由增量编号为 V074，清理其旧编译副本。未改写 Flyway 历史或清库。

## 验收方法

实操脚本 `tools/dev/feedback_prototype_e2e.mjs` 使用独立 CAS 用户、真实浏览器、真实上传、真实业务请求和持久化回读。音频及模型场景按该次文件 SHA256/精确请求隔离，结束后删除该次场景；不通过 SQL 灌入提交成功或审核成功结果。故障场景先让真实提交成功，再故意丢弃响应，用刷新后的原 key/body 恢复。

数据库回归 `tools/dev/feedback_repair_check.py` 只创建独占临时数据库，迁移、测试后删除；同时间混合分页和即时失效等边界数据仅在该独占库构造。使用独立 Maven 输出目录，避免共享 target 被其他构建覆盖。服务重启和实际浏览器测试遵循项目生命周期锁。
