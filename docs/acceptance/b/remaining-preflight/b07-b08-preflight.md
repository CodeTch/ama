## Approved business rules to preserve

1. Generate only from the current saved confirmed transcript, including its complete marks, source chain, archived processing configuration and fixed confirmation hash. Empty materials are explicit; name/category need not block generation. Name/category and other final readiness conditions do block final confirmation.
2. Output has exactly the seven categories OVERVIEW, DISCUSSION, CONCLUSION, ACTION, RISK, OPEN_QUESTION, DISAGREEMENT, plus the separate sensitivity/background directories. Empty categories remain represented. Invalid JSON/schema, duplicate keys, invalid Unicode/anchors, out-of-bounds or nonexistent sources, extra/missing source aliases and unsupported scope reject without partial acceptance.
3. `CreationSupport` initializes only PARTIAL/UNSUPPORTED. Structural validity does not establish truth. Conclusions/actions require meeting evidence; background alone is insufficient. ACTION suggestions do not populate accepted enterprise owner/date or grant meeting access.
4. First successful generation may automatically save only when no valid body exists, no editor has intervened and the version is unchanged, under one atomic fresh permission/lifecycle/version check. Re-generation always remains a candidate until explicit owner adoption. A task's success is distinct from adoption success. Concurrent input must survive, and duplicate/late completion never repeats adoption.
5. Human reviews bind the exact saved target content/version/anchor, the entire relevant evidence set, profile and current owner identity/time. Latest matching exact scope wins; partial spans cannot combine into full credit implicitly. SOURCE_SUPPORT and ACTION_FIELDS are independent. Evidence insufficiency can become an OPEN_QUESTION through an explicit new saved revision; that editing operation itself must have an implemented provenance path.
6. Final confirmation uses saved content, fixed current metadata/roster/transcript/material/template/exclusion/element/body versions, no pending candidate/material changes, no generation debt or sensitive conflict, and exact valid reviews. Freeze chosen `final_result_review` IDs in the same transaction; historical reads never recalculate membership using latest reviews.
7. Published content becomes permanently read-only (`ever_published` never resets). All write APIs, task application and file/reference mutation paths must respect this, not only the publication page. Withdrawal/obsolescence does not make content editable or publishable again.
8. UNKNOWN publication is locked for reconciliation, never a request to resend. External business key is a stable encoding of publicationId plus confirmationId. One publication root per meeting survives zero-effect retries. Same-key/different-request conflicts and all replay paths still require current authorization.

## B06/B05 dependency contracts and unresolved seams

### A. Authentic B06 source and confirmation

Require B06.3's upload UUID/purpose, completed session, AVAILABLE file, storage route/epoch, current/history qualification, retained references, and held-capability read/recheck interface. Then require actual TXT parsing, immutable output/segments/marks, working save/restore and current confirmation API. Do not directly insert hand-written `transcript_confirmation` rows and call the vertical flow integrated.

B07 needs a bounded complete facts reader returning detached `StoredProvenanceFacts` plus explicit current guard facts and a finite dependency closure. It must include actual matching TaskSpecs, original producer tasks, source files and immutable history, not DTO summaries or caller-supplied versions. Count/byte/UTF8-scalar/UTF16/graph/depth/cancellation bounds apply before allocation and across the whole closure. Excess rows fail, never truncate. B06's processing reader is a pattern and reusable component, not a full minutes reader.

Read/archive/parse/hash outside write transactions; inside the owned write transaction reacquire authentic identity/access and compare current fences and every relevant persisted immutable fact. Complete identities precede subject/root, then domain rows, tasks, operations/executions, audit/outbox. Use the same exact DataSource object and authentic `JdbcTaskPreparations` issuer/holder/full-spec/purpose token. Policies must implement batch `lockRoots` where shared roots would otherwise be rediscovered. No archive/file/model/network calls while holding DB locks.

### B. Atomic output creation is not already solved

`JdbcTaskQueue.completeWithEffects` invokes `validateOutput` before `effects.run()`. `JdbcExternalOperations.observe` does the same in its canApply path. A validator expecting an already-persisted candidate cannot validate a row first created by that callback. Pre-saving output in an unrelated transaction defeats atomicity.

Recommend a shared reviewed prepared-result protocol: bounded parse/semantic preparation outside locks; under the owning transaction validate genuine input/capability/fence, persist the full output closure, validate the saved output reference, then finish task/operation and audit/outbox. All roll back together. API shape may be a constrained prepared completion or domain-owned transactional writer; do not approve an arbitrary caller Supplier as authority. B06 owns the common task/worker seam, B07/B08 consume it. Cover both queue completion and authoritative external observation; changing only one leaves the other gap.

`WorkerLoop.Handler` currently returns `TaskResult` and WorkerLoop then calls `queue.complete`. A handler that independently finishes through external observation must not also be treated as an ordinary second completion. Introduce an explicit supported execution/completion mode with one owner, retain heartbeat/lost-lease behavior, and test at the WorkerLoop level.

### C. Preserve candidate versus fence changed business effects

`validLease` and external `canApply` require `q.current` businessVersion/cancelEpoch. Ordinary saved edits advance meeting/subject versions. Therefore an edit while generating currently prevents all domain effects, including candidate insertion. The UX requires retaining candidates when the auto-save guard fails; a bare callback cannot deliver that behavior.

Recommend a narrowly reviewed domain retention path distinguishing (a) immutable result retention for the original input, under current authentic owner/read authority and valid lifecycle/cancel epoch, from (b) current-body adoption under the original expected revision/fingerprint/editor guard. Generic B05 fence rules stay intact. Cancellation/deletion/revocation must not be converted into permission to save or expose content. A receipt-only external fact remains receipt-only. Define whether a retained obsolete candidate is PENDING or STALE and its explicit disposition; do not silently rebase its original input/adoption fence. Before this path exists, qualify only current-fence completion, and do not claim concurrency-candidate preservation complete.

### D. 'Nobody editing' needs a server-observable contract

V008 `meeting` has revision/pointers/needs_generation but no minutes editing-intent/session/epoch field. Saved-edit CAS proves only that no saved edit won. A browser's unsaved typing is not observable from `minutes_revision_id IS NULL`.

Recommend a durable monotonic first-save suppression/editor-intent guard, acknowledged before UI enables editing during generation; snapshot it with the generation request and recheck atomically at first save. A new intent invalidates auto-save eligibility without deleting the candidate or draft. This needs an explicitly reviewed API/storage and B09 handshake; a local memory flag, client `notEditing=true`, or expiring heartbeat alone cannot prove no concurrent draft. Decide its relation to business-version changes together with candidate retention above. Conservative permanent suppression for a given first-generation attempt costs a manual adoption after an abandoned editor but protects user input. Until implemented, candidate-only delivery is a partial runtime slice, not compliance with approved auto-save UX.

## B05 integration: exact reuse and limits

- Generation external calls also consume `ExternalOperationPort.beginExternal` and token-bound `ModelPermitPool.acquire`; a local thread/pool semaphore alone is not global model admission. Commit marker before network. A timeout does not prove zero side effect or settle a permit. Only verified terminal facts settle; missing company cutoff/lookup/cancel semantics must remain UNKNOWN/manual-required with conservative capacity retention.
- Reconciliation uses its own durable token/epoch/heartbeat and performs query outside DB locks. Reuse `ReconciliationLoop`; do not turn unknown into a new task send. B06.1 permits narrowly verified terminal fact receipt when domain effects are forbidden; do not restore owner or business authority from that receipt.
- `DomainPreparationUnavailableException` / `ObservationRetryRequiredException` mean the same fact was not acknowledged; preserve and resubmit that fact after configuration/rediscovery. They never justify another external call. Ordinary operational/database exceptions must not be swallowed as stale.
- Knowledge publish FAILED maps to retryable business state only if the normalized adapter can establish definitive zero effect. Generic HTTP error, connection close, timeout or eventual-consistency not-found is not that proof. Normalize with existing `NoEffectProof` and authoritative verifier, not a trusted caller status.
- Publication READY/RUNNING/RECONCILING/FAILED/SUCCEEDED maps external UNKNOWN to RECONCILING. `publication_attempt` must retain exact operation/execution/confirmation. Read-only irreversible state follows verified success even if the original task lease expired; if business application is fenced, preserve the authoritative fact and require controlled reconciliation/manual handling without a resend or forged local published pointer.
- Existing `LIMIT 64` reconciliation candidate fairness follow-up remains OPEN. A controlled finite-window reconciliation test does not demonstrate eventual service beyond the window or production fairness.

## Forward design/schema deltas and safe choices

1. Editor-intent guard above is a real schema/API design gap. Register a forward change centrally only after precise lifecycle/version/UI handshake and tests are reviewed; preserve V008/V012.
2. Candidate retention and prepared output are shared protocol deltas; first determine whether capabilities/transactions alone suffice or any persistent status/receipt fields are needed. Do not weaken generic fencing or write unattached model JSON to make output validation pass.
3. D01 adopted design adds `source_context`, `source_context_material`, `parsed_document_profile`, and nullable origins on minutes elements/evidence. New catalog v2, rowset v2, generation/review/final v3 and new generation-root definition schemas are required; old 15 profile kinds and exact old bytes/digests remain. Implement new version dispatch explicitly, never reinterpret legacy hashes or infer parser format from PAGE/PARAGRAPH.
4. Basis versus evidence is essential even for zero-evidence or rebound-evidence elements: every included element's immutable source context is a basis root. PINNED includes saved-set bases and set usages, excludes body/applied exclusions; REVIEW includes the selected element basis and exact intersecting evidence; FINAL includes all frozen bases and body/set/directory/applied-exclusion usages. Complete context/material/profile closure is checked and retained. Basis creates neither evidence occurrence nor support credit. The current S1 v2 subset does not implement these v3 shapes.
5. Current final helper takes a `FinalFacts` row whose `source_manifest_hash` is an output field. The service needs an explicitly reviewed prospective-final computation boundary or a clearly documented projection that excludes output-only fields; no fake stored-success placeholder. Actual saved verification remains strict afterward.
6. V013 already handles one publication root and exact attempt execution references. No speculative new publication table is needed merely to implement first controlled flow. Correctly allocate/update operation/execution/attempt rows through the shared transaction protocol; never fabricate IDs for noncommitted external facts.

Choosing the initial transcript-only profile reduces parser/schema work and enables early real DB/HTTP orchestration evidence. It does not remove D01 requirements. Implementing the persistent editor guard and shared retention/atomic completion seam costs additional design/IT work now but avoids an unsafe first-save shortcut and later incompatible queue patches. Company missing contracts block true qualification, not these independent domain/test slices.
