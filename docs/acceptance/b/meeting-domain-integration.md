## HTTP and saved values

The production API adds POST `/api/v1/meetings {}`, GET `/api/v1/meetings/{id}`, PUT `/api/v1/meetings/{id}/info`, and POST `/api/v1/meetings/{id}/roster-confirmations`. The OpenAPI source is `contracts/openapi/meetings.yaml`, referenced by the root document; generated TypeScript is updated. There is no list/search route. Identity comes exclusively from the existing opaque shared session; writes retain exact Origin and session CSRF enforcement. All responses inherit no-store. Unknown fields, duplicate JSON fields, nonintegral/missing revisions, missing/duplicate idempotency headers and malformed Unicode are rejected.

Creation returns `{id,revision:0,stage:"ENTRY"}` and persists an empty immutable info revision and empty roster draft. Actual date remains null. Save returns `{id,revision}` and accepts complete human values: `expectedRevision`, optional nullable `name/category/summary/occurredOn`, required `rosterDraftIds` containing exact enterprise IDs, and optional `externalRosterNames` (default empty). Optional omitted text/date is null, not a patch. No name/summary product character limit is added. `meeting.http.max-request-bytes` is a separately configurable transport budget, default 8388608 bytes, returning 413 without truncation or consuming a key; Jackson's separate string-length cap is disabled. This is a body acceptance budget, not a preallocation/streaming memory guarantee. Directory display names are copied from the locked shared identity rows; browser-supplied enterprise display names/owners/roles are not accepted. External names are display-only: neither external identity matching nor email authorization is invented.

The production `CategoryDictionary` port remains unavailable for every non-null category until an actual approved local configuration/company snapshot is provided. Implementations must be local and perform no network I/O inside the transaction. Empty drafts and null categories remain supported. Only the controlled test composition recognizes its explicitly test-only dictionary entry.

Saving information never changes effective grants. A different roster set (exact ID/name/kind with multiplicity for external names) creates a new immutable DRAFT. No-op roster values retain the latest roster version. Explicit confirmation requires a pending latest draft, fresh ACTIVE identities, and current aggregate CAS; it creates a new immutable CONFIRMED copy at the new aggregate revision, leaving the source draft intact. Selecting the latest **all-state** roster, rather than MAX(DRAFT), means the historical draft is no longer presented as pending after confirmation. Empty confirmation is legal before name/category/date are populated. Later draft changes retain the previous confirmed pointer and grants until another confirmation commits.

GET returns the current valid saved info and current confirmed roster. Only the owner receives `rosterDraftId/rosterDraft` for an actual pending latest draft; both fields are null for members and when confirmation supersedes the draft. Current valid enterprise members are READ-only. Platform admin roles and legacy `meeting_acl`, including timestamped rows, never grant body access. ACTIVE lifecycle and governance are required for ordinary reads, consistent with the adopted database design's denial of ordinary recall/download/search during withdrawal/obsolescence, including pending states. Published/ever-published meetings cannot be mutated. Historical versions are never deleted. Later B06–B08 owners still implement result/final/publication projections; this GET does not expose speculative result references.

## Transaction composition and lock contract

`MeetingService` and `RosterService` commands own independent B01 `TransactionRunner` transactions and reject ambient transactions. Every production component uses the exact same DataSource instance. The order is:

1. Insert-or-lock the idempotency scope row, then read its complete digest/result.
2. Lock the complete discovered identity set in unsigned UTF-8 byte order, including the actor, new desired members, current draft members and current grants. Check the actor against the current shared ACTIVE row, never `Actor.status` or roles.
3. Create/lock the B05 MEETING subject, then lock the actual meeting root. Existing root revision/cancel epoch must match its fence. Creation inserts the fence before its root.
4. Check owner permission, current CAS, lifecycle/governance/publication state and full currently affected identity coverage. A lock-free discovery race—including a guessed future expectedRevision—cannot cause late identity locking: missing coverage produces 409 and rolls back the entire attempt. Never use SKIP LOCKED for ACL or complete rosters.
5. Append immutable versions, replace the effective grant set during confirmation, update the root and projection, advance the subject, and complete the idempotency result. Information saves clear the current final-confirmation pointer while preserving history.
6. Append B01 metadata-only audit and the real domain event, then call the B05 `outbox.flush()` as the final lock/write operation. Return only in-memory safe ID/revision/status values afterward.

Standalone `MeetingAccess.require(actor,id,action)` owns its transaction and refuses an ambient transaction. A domain caller that already owns a transaction must acquire `MeetingAccess.Locked gate = access.lock(actor,id)` **at its initial identity/subject/root prelock phase**, then call `access.require(gate, action)` within that same transaction. The latter does not acquire a new identity or root: it re-reads the already-held root and validates current roster provenance, preventing cached governance/pointer decisions. The opaque handle is bound to its issuing access adapter, exact DataSource and actual Spring transaction holder. Old transactions, foreign issuers and fabricated handles are rejected. Re-entering this adapter's identity prelock after it has begun subject/root locking is rejected. No additional transaction synchronization is registered, preserving B05's sole final-flush synchronization.

As with the B05 composition contract, arbitrary caller SQL outside the supported API cannot be intercepted. A caller that manually locks a root first and then calls `access.lock(actor,id)` is outside the contract; use the pre-acquired capability. Do not call a standalone service or access method from a queue callback. For callbacks, prelock identity/subject/root in the owning domain policy before task locks and reuse that transaction's capability; no network work or discovery of another root is allowed. This delivery does not add a production worker/provider registration.

## Idempotency, versions and provenance

Scope SHA-256 uses four-byte big-endian UTF-8 byte lengths for actor/resource/operation/key. The request digest uses a versioned complete typed semantic encoding, including null markers, revision, every text/date field and all roster values/list sizes; no body prefix is used. Invalid surrogate input is rejected instead of being replaced during UTF-8 hashing. JSON formatting differences and omitted optional values have the documented semantic meaning. Keys have no history TTL.

The unique insert waits for a concurrent winning transaction. A transaction-local incomplete result is never committed: domain failure, bad audit or failed final outbox flush also rolls back its idempotency row. After identity/root authorization, digest mismatch returns 409. Same-body replay rechecks current authorization and returns the original operation result without applying effects. `result_id` points to the original immutable info revision (create/save) or confirmed roster copy (confirmation), from which exact meeting ID and aggregate revision are recovered. This works after subsequent edits/confirmations and needs no V008 schema amendment. Create's original status/stage is always 201/ENTRY; saves and confirmations return 200 with the original revision.

`MeetingEventReferences` registers production kinds `MEETING_INFO` and `MEETING_ROSTER`, never B05 TEST_* kinds. Created/saved events require an exact immutable info row and current matching root revision/pointer; confirmed events require an exact CONFIRMED roster and current matching pointer/revision. Subject kind, event meaning and null task ID are validated. No fabricated task or domain reference is inserted. Events contain metadata only.

`meeting_search_projection` always retains the full persistent UUID number, current saved name/category/info pointer, current confirmed roster pointer and current aggregate revision. `meeting_person_search` is replaced only during explicit confirmation, from that confirmed roster. Old names and pending/external drafts cannot contaminate the current effective search set. D02 owns the eventual common-F list/search implementation.
