# B04 S3 file infrastructure

This is a DB-free adapter and a controlled local-provider qualification. It does not install a production bean, choose a production provider, certify business availability, or create database/API/configuration UI behavior. Production durability, capacity, HA, backend-registry governance and controlled MySQL/B04 integration remain separate gates.

## Construction and runtime

`ama.storage.s3.S3FileStorage` implements the unchanged nine-method `FileStoragePort`; `resume(UploadToken)` also helps a previously frozen completion using only the original token and the same fixed backend definition. Construction requires an explicit `S3Config`: logical backend ID, stable endpoint, region, separate data/control buckets, credentials, addressing mode, physical budget, bounded staging/native profile, request admission and finite timeouts. There is no environment/default credential chain or ambient HTTP proxy. Mutating SDK retries are disabled. Credentials and timeouts do not select historical scope; the static physical configuration is bound in full to each scope/key. Repointing an existing physical definition to unrelated storage is unsupported.

The Maven BOM is AWS SDK **2.56.0**, with `s3` and `url-connection-client`. Apache, Apache5 and Netty clients are excluded. The existing native file-service dependency edge excludes both new SDK entry modules; its executable must remain free of the S3 runtime. The qualification profile uses 8 MiB staging chunks, native minimum 5 MiB, native maximum 5 GiB, at most 10,000 native parts, request admission 8 and 20-second SDK timeouts. Its 50 GiB admission value is a technical test configuration, not evidence of a tested 50 GiB object, a product file-size limit, or production throughput.

## Protocol and recovery

The implementation is split into transport/admission (`S3Objects`), physical identity (`S3Layout`), bounded chunks (`Staging`), selected logical manifests (`SessionJournal`), verified random-access publication sources (`PublicationSource`), native conditional publication (`NativePublisher`) and HEAD/range handling (`RangeReader`).

Native streaming requests reserve one shared admission slot for the staging reads performed by their request bodies. A real SDK barrier test with admission two first reproduced both concurrent native publications timing out while waiting for their own staging permits; the separate native-request gate permits progress while keeping total active requests within the configured bound.

Each logical part is stored as immutable bounded chunks, descriptor pages and a canonical root. A single conditional accepted slot returns the original stable receipt on identical replay. Completion validates exactly the caller-selected ordered receipt list, including actual bytes and the whole SHA-256, before competing for one immutable terminal object. Accepted but unselected empty or nonempty parts are excluded. The only terminal alternatives are ABORTED and COMPLETE; competing complete manifests must match the original fingerprint. Late part slots cannot acknowledge after a terminal decision. Complete helpers do not introduce a second terminal state.

Every helper uses a new native attempt intent and native upload ID. Known IDs are journaled before uploading parts. An uncertain CreateMultipartUpload response leaves the intent and any provider upload intact; the adapter never guesses an ID from a listing. Logical parts are coalesced into legal native intervals, including zero/tiny/mixed parts and more than 10,000 logical parts. Small and empty final objects use conditional PUT. All final PUT and CompleteMultipartUpload requests carry `If-None-Match: *`. Lost responses, embedded HTTP-200 errors, 409, 412 and NoSuchUpload are reconciled against the exact final object's actual bytes. No ETag, user metadata or result record substitutes for content SHA-256.

Before publication, `PublicationSource` verifies every accepted root/page and every actual byte, and builds at most 10,000 interval positions. It retains only interval starting roots/offsets, not the whole logical manifest. SDK reopens seek directly to a verified staging chunk; every fetched chunk is again checked against its descriptor SHA/length. The final object is also hashed after publication. Recovery rebuilds the index from durable selected records; no local file, process lock or heap cache is required. Control objects and completed/unknown attempts are retained conservatively. Automatic orphan cleanup, object-version reclamation and guessed aborts are not implemented.

## Layout v3 and listing

The approved layout is `data/v3/<scope SHA>/P(F(objectKey))`. Scope hashing uses exact, length-prefixed UTF-16 backend/namespace/config identity. Immutable `scopes/v3/<H>/spec` and `keys/v3/<K>/spec` objects compare full canonical bindings, including physical routing fields; a digest match alone is insufficient. Missing scope lists empty. Malformed or mismatching binding fails closed, including forced scope collisions. Delete requires an existing matching key binding and never removes an unbound physical object.

`F` encodes period as `.0`, logical slash as `.1`, and tilde/higher UTF-16 units as `~hhhh`. Other permitted ASCII remains literal. `P` chunks the complete encoded stream every 199 characters, prefixes each physical segment with `x`, and joins with `/`. Escapes may cross a physical boundary. Decoding rejects alternate segment lengths, missing markers, malformed escapes, noncanonical hex, invalid logical keys and wrong scope. The transformation preserves exact Java code-unit identity, order and literal-prefix semantics, including unpaired surrogates.

The final length is `72 + L + 2*ceil(L/199)`, where L is the encoded length. L=942 occupies exactly 1,024 bytes; L=943 is rejected before I/O. Every physical segment is at most 200 bytes and total depth at most eight. Ordinary 512-character alphanumeric/underscore/hyphen keys fit without caller segmentation, including 64-character backend and namespace identifiers. A slash-rich valid 511-character logical key has only seven physical levels. Escape-heavy legal generic keys may be unrepresentable and receive technical INVALID_ARGUMENT without truncation or a hash fallback. No current application key generator is implemented or claimed verified merely from a database column's size.

Listing issues one ListObjectsV2 page with independently derived scope/prefix and `MaxKeys <= limit`; there is no delimiter, auto-paginator, namespace scan or external index. A logical prefix ending at encoded position 199 has no trailing physical slash, so the exact key and its extensions coexist. Only returned-page objects are content-hashed. The v3 cursor binds static config, backend, namespace, scope H, logical prefix, provider continuation and last canonical physical key. It rejects v2 or foreign-scope cursors and validates provider order/progress. Concurrent deletion can produce short/empty advancing pages; enumeration is not a snapshot.

All control keys are validated before I/O: ASCII, <=1,024 total bytes, <=200 bytes per segment, <=8 segments, no empty/dot/dotdot segment. Templates are scope/key `spec`; session `spec`, `parts/<number>`, `terminal`, `result`, `completions/<fingerprint>/page/<number>` and `/root`; native `attempts/<UUID>/intent` and `/known-upload`; staging `<owner UUID>/<candidate UUID>/chunk/<number>`, `/manifest-page/<number>` and `/root`. The deepest template has seven segments. User-derived scope/key text appears only in bounded canonical payloads.

## Bounded reads and measured replay

`read` validates numeric arguments, exact bindings and HEAD metadata, then issues only the requested range. Concrete VersionIds are pinned; never-versioned or suspended/null versions use the opaque HEAD ETag as If-Match. It checks 206, exact Content-Range/length, version and validator, and rejects ignored or malformed range responses. Zero-length reads issue no final GET. Stream closure/error calls abort and releases request admission without draining the object. `stat` intentionally reads and hashes the full object; range reads never call stat.

The real HTTP proxy measures upstream payload separately from delivered payload and records allowlisted signed request headers. Three one-byte reads transfer exactly three final body bytes. Tests use both 16 MiB and 64 MiB objects; early close and rejected range responses have a fixed transport-window allowance below 1 MiB, not full-object drain. Raw wire captures and exact figures are in the implementation report.

The original replay-from-start implementation failed a real amplification test: 16 MiB/4 native parts read 75,497,472 staging bytes (4.5x), while 64 MiB/13 parts read 587,202,560 bytes (8.75x). The indexed implementation reads 293,601,280 bytes (4.375x) for the same 64 MiB case and preserves 4.5x at 16 MiB. Counts include staging verification and actual SDK replay; final-object stat is separately counted. The 8x test allowance is for this pinned profile, not a universal production performance SLA.

## Local evidence and boundaries

The solely owned fixture is RustFS **1.0.3**, linux/amd64, digest `sha256:128220dc9382bac81940a1a9616ee8c274a3f3b8f647eedbeb50df5bb8b49922`, limited to 2 CPU/2 GiB/256 PIDs, with console disabled and an owned fixed loopback endpoint. Credentials/data stay under ignored `.tools/`, with private credential files and UID-10001 data directories. The helper verifies exact container ID, ownership label, image, mount paths and port binding before restart/stop. Every test fixture receives fresh data/control buckets and a distinct physical configuration. There is no fallback or token redirection between fixtures.

The retained v2 attempt exposed a real provider limitation: single physical segment 255 succeeded and 256/512/1024 failed. A deep raw diagnostic was followed by exit 139, OOMKilled=false, and a restart stack-overflow failure. That does not establish the precise causal code path. The failed container/data, raw diagnostic and all failures remain retained; no deeper probe is repeated and no old object/token is reinterpreted as v3. A source-only v2 archive preserves its implementation and evidence identity.

The new v3 restart fixture uses fixed loopback port 44789. Five acknowledged objects include a 512-character logical key published by a real >9 MiB native MPU, the exact 1,024-byte shallow key, valid slash-rich key, and 199/200 boundary keys. After its exact owned container restarted, a fresh JVM checked all full bytes, HEAD/ranges, bounded listing, original-token resume and exact-key delete. This qualifies those local scenarios; it does not explain or repair the retained old provider failure, establish power-loss durability, or certify production HA.

Shared FileStorageContractIT assertions are preserved and run separately through the real native local process/disk and the real Java SDK/S3 path. The selector is `AMA_STORAGE_CONTRACT=s3`; default is local. Historical display labels still say `local`, so the selected fixture and command are part of the evidence. The canonical IT runner requires the already approved test-environment admission variable; sourcing that fixture's environment for these storage selectors does not connect to or modify MySQL. Existing reactor unit tests independently exercise their own H2 TCP outage and deliberately unreachable loopback MySQL probe; this is not a controlled MySQL-fixture test.

The coordinator's `task-B-04-s3-implementation-report.md` records actual commands, fresh counts, source/classpath identities, retained failed attempts, dependency/package inspection and final independent review status. Raw evidence remains under ignored `artifacts/phase-b/b04-s3/`; acceptance is not inferred from a stub, skipped suite, raw PUT alone or a plan.

At the initial implementation handoff (`9a8b79d`), the canonical reactor units passed 38 tests, the shared local and S3 contracts passed seven each, the related S3 regression passed 23, and the added overlong Content-Length/range case passed. The separately frozen v3 10,001-logical-part test passed with a 384 MiB Java heap and one conditional final PUT; its historical v2 counterpart also passed and remains separate. The frozen-to-`9a8b79d` production bytecode comparison differed only in missing-binding delete and native admission paths, with independent regressions for both; the small-PUT coalescing, layout, selected-manifest and indexed-source instructions were unchanged. That historical source/evidence seal remains immutable.

Independent review identified missing nullable Content-Length validation. The review fix rejects absent/negative structural lengths with STORAGE_UNAVAILABLE before reading bodies and retains cleanup ownership until a validated range wrapper is returned. Real close-delimited and chunked 206 faults, missing HEAD length and all actual-byte reader paths are tested; repeated malformed responses beyond the admission budget must leave the same adapter able to serve a healthy read. The SDK configuration now uses the supported `StandardRetryStrategy` with `maxAttempts(1)` consistently in production and fixtures. Test capture uses synchronized amortized-constant-time append with immutable settled snapshots; no historical 10,001-part run was repeated or reinterpreted. The fixture's read-only ownership check now verifies exact container ID, CPU, memory/swap and PID bounds before an authorized restart/stop. Fix-round source and evidence are separate from the initial seal and still require scoped independent review; production acceptance remains outside this delivery.
