# 线上模型服务接口文档

本文根据提供的 `offline_client_v1.py` 调用示例，以及 `offline_pipeline 2` 中的 `offline_client.py`、`llm_correct.py` 整理。示例中的结果仅用于说明格式，不代表真实识别结果。本次未对线上服务逐一进行实测；没有在调用示例中确认的服务端行为，均单独注明。

## 1. 接口概览

| 功能 | 方法 | 默认地址 | 请求体 | 返回值 |
| --- | --- | --- | --- | --- |
| VAD 语音活动检测 | POST | `http://192.168.124.227:8000/vad` | JSON，含 Base64 WAV | `segments` |
| SPK 说话人分离 | POST | `http://192.168.124.227:8001/diarize` | JSON，含 Base64 WAV 和 VAD 结果 | `timeline` |
| SPK 声纹向量 | POST | `http://192.168.124.227:8001/embed` | WAV 二进制 | `embedding` |
| ASR 语音识别 | POST | `http://10.14.72.51/inference/asr-nano/modelserving/asr` | WAV 二进制 | `text` |
| 标点恢复 | POST | `http://10.14.72.51/inference/asr-punc/modelserving/punc` | JSON 文本 | `text` |
| LLM 文本纠错 | POST | `http://10.14.72.51:30080/v1/chat/completions` | JSON 对话 | `choices` |

地址是客户端配置中的内网地址，需要在能访问对应网络的环境调用。实际地址可通过客户端参数调整。

### 通用约定

- VAD 和说话人分离使用 `Content-Type: application/json`；ASR 和声纹向量使用 `Content-Type: application/octet-stream`；标点及 LLM 使用 JSON。
- 模型服务客户端默认在 VAD、SPK、ASR、标点请求中设置 `Host: inference.dev.zsfund.com`。这是调用示例中的配置，是否必须取决于服务及网关部署；LLM 调用不自动添加此 Host。
- 音频按客户端实际处理方式统一为 **16 kHz、单声道、16 位 PCM 编码的 WAV**。JSON 中的 `audio_b64` 是完整 WAV 文件字节的 Base64 字符串，不是文件路径，也不带 `data:...` 前缀。二进制接口直接发送完整 WAV 字节，不是 Base64，也不是 multipart 上传。
- 以下时间均按客户端使用方式记为毫秒。VAD 和说话人分离的时间相对整段输入音频；ASR 可选字级时间戳相对该次提交的音频片段。
- 线上调用示例未提供 VAD、SPK、ASR、标点的鉴权信息，不能据此断定线上部署无需鉴权。

## 2. VAD 语音活动检测

识别整段音频中有语音的时间区间。

**请求**：`POST http://192.168.124.227:8000/vad`

```json
{
  "audio_b64": "<完整 WAV 文件的 Base64 字符串>"
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `audio_b64` | string | 完整 WAV 音频字节经过 Base64 编码后的字符串。 |

**响应示例**：

```json
{
  "segments": [[100, 2500], [3200, 5600]]
}
```

`segments` 是语音区间数组；每项为 `[开始毫秒, 结束毫秒]`。将返回的数组原样传给说话人分离接口的 `vad_segments`。

## 3. SPK 说话人分离

对整段音频中的语音区间进行说话人聚类，输出各说话人的时间线。

**请求**：`POST http://192.168.124.227:8001/diarize`

```json
{
  "audio_b64": "<完整 WAV 文件的 Base64 字符串>",
  "vad_segments": [[100, 2500], [3200, 5600]]
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `audio_b64` | string | 与 VAD 使用的同一份完整 WAV 音频的 Base64 字符串。 |
| `vad_segments` | array | VAD 返回的 `segments`，每项为 `[开始毫秒, 结束毫秒]`。 |

**响应示例**：

```json
{
  "timeline": [[100, 2500, 0], [3200, 5600, 1]]
}
```

`timeline` 每项为 `[开始毫秒, 结束毫秒, 说话人编号]`。编号用于区分本次处理中的不同说话人，并非真实姓名；要对应姓名还需结合声纹库比对。

当前 `offline_client.py` 在指定参数时还可能发送 `speaker_count`（指定人数）、`min_speakers`（人数下限）、`pval`（聚类参数）。提供的线上 v1 示例未使用这些字段，**不能确认线上服务是否支持或生效**，需与服务端核实。

## 4. SPK 声纹向量提取

从说话人音频中提取声纹向量。该接口只返回向量，不直接返回姓名。

**请求**：`POST http://192.168.124.227:8001/embed`

请求体是完整 WAV 二进制，`Content-Type: application/octet-stream`。

```bash
curl -X POST 'http://192.168.124.227:8001/embed' \
  -H 'Host: inference.dev.zsfund.com' \
  -H 'Content-Type: application/octet-stream' \
  --data-binary '@speaker.wav'
```

**响应格式示例**：

```json
{
  "embedding": [0.12, -0.08, 0.31]
}
```

`embedding` 为浮点数数组。示例只展示格式，不表示实际向量长度；与声纹库做比对时，向量维度及模型需兼容。客户端会收集、拼接同一说话人的音频后再提取向量，默认目标采样时长为 50 秒，这是客户端策略，不是已确认的服务端要求。

## 5. ASR 语音识别

将语音音频转换为文字。

**请求**：`POST http://10.14.72.51/inference/asr-nano/modelserving/asr`

请求体是完整 WAV 二进制，`Content-Type: application/octet-stream`。

```bash
curl -X POST 'http://10.14.72.51/inference/asr-nano/modelserving/asr' \
  -H 'Host: inference.dev.zsfund.com' \
  -H 'Content-Type: application/octet-stream' \
  --data-binary '@segment.wav'
```

**响应示例**：

```json
{
  "text": "大家好，今天我们开始开会。"
}
```

`text` 为识别文字。当前客户端按默认最多 30 秒合并音频片段再提交，这是客户端策略，不代表服务端的硬性长度限制。

当前客户端也会尝试读取可选的 `tokens`，格式预期为 `[[字, 开始毫秒, 结束毫秒], ...]`。提供的线上 v1 示例只读取 `text`，**不能确认线上 ASR 是否返回 `tokens`**；没有该字段时，客户端会使用其他方式分配说话人。

## 6. 标点恢复

为识别文本补充标点。

**请求**：`POST http://10.14.72.51/inference/asr-punc/modelserving/punc`

```bash
curl -X POST 'http://10.14.72.51/inference/asr-punc/modelserving/punc' \
  -H 'Host: inference.dev.zsfund.com' \
  -H 'Content-Type: application/json' \
  --data-raw '{"text":"大家好今天我们开始开会"}'
```

**请求参数**：`text`，字符串，需要补标点的文字。

**响应示例**：

```json
{
  "text": "大家好，今天我们开始开会。"
}
```

返回的 `text` 为处理后的文字。如果 ASR 结果已包含足够标点，客户端可能跳过该接口；如果响应中缺少 `text`，客户端保留原文。

## 7. LLM 文本纠错

客户端使用兼容 Chat Completions 格式的接口进行转写纠错。接口请求内容实际由业务提示词动态生成，下面仅展示调用结构。

**请求**：`POST http://10.14.72.51:30080/v1/chat/completions`

```json
{
  "model": "deepseek-v4-flash",
  "messages": [
    {"role": "user", "content": "请检查以下会议转写中的识别错误：……"}
  ],
  "temperature": 0
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `model` | string | 模型名，客户端默认 `deepseek-v4-flash`，可配置。 |
| `messages` | array | 客户端发送一条 `user` 消息，`content` 为完整业务提示词。 |
| `temperature` | number | 客户端固定为 `0`。 |

**响应格式示例**：

```json
{
  "choices": [
    {"message": {"content": "模型返回的文本"}}
  ]
}
```

客户端读取 `choices[0].message.content`；纠错结果的具体内容由提示词及模型决定，不能将上述占位文本当作固定业务返回格式。

地址可通过 `--llm-url` 或 `LLM_CHAT_URL` 配置，模型可通过 `--llm-model` 或 `LLM_MODEL` 配置。客户端有可用密钥时发送 `Authorization: Bearer <密钥>`；优先使用 `LLM_API_KEY`，否则可能回退到已有的 DashScope 密钥配置，没有可用密钥时不发送鉴权头。请勿将真实密钥写入文档或示例。

## 8. VAD 与说话人分离调用示例

以下示例使用 Python 标准库，读取同一份 `meeting.wav`，依次调用 VAD 和说话人分离。请先确认音频格式符合本文约定；示例不会自动转换音频。

```python
import base64
import json
from pathlib import Path
from urllib.request import Request, urlopen

host = "inference.dev.zsfund.com"
audio_b64 = base64.b64encode(Path("meeting.wav").read_bytes()).decode("ascii")

def post_json(url, payload):
    request = Request(
        url,
        data=json.dumps(payload).encode("utf-8"),
        headers={"Content-Type": "application/json", "Host": host},
        method="POST",
    )
    with urlopen(request, timeout=1800) as response:
        return json.load(response)

vad = post_json("http://192.168.124.227:8000/vad", {"audio_b64": audio_b64})
print("VAD:", vad["segments"])

spk = post_json("http://192.168.124.227:8001/diarize", {
    "audio_b64": audio_b64,
    "vad_segments": vad["segments"],
})
print("说话人时间线:", spk["timeline"])
```

## 9. 超时与排查

| 调用 | 当前客户端等待超时 |
| --- | --- |
| VAD、说话人分离 JSON 请求 | 1800 秒 |
| ASR、声纹向量二进制请求 | 600 秒 |
| 标点恢复 | 300 秒 |
| LLM 首轮纠错 / 语义复核 | 180 秒 / 60 秒 |

这些数字是客户端等待设置，不是服务端处理时长保证。连接失败时检查内网可达性、地址、端口与 Host；调用失败时检查 HTTP 状态及服务端返回内容；结果异常时检查音频采样率、声道、编码、时间单位和声纹模型兼容性。示例未确认统一错误码或响应结构，具体错误以服务端实际返回为准。

## 10. 与旧版接口的区别

本文的 `/vad`、`/diarize`、`/embed`、`/asr`、`/punc` 对应 `offline_client.py` 的 `online` 模式和提供的线上调用示例。项目还保留 `legacy` 模式，使用 `/v1/...` 路径，其整段音频使用 `audio_url`，部分片段接口使用裸 PCM，不能将本文线上请求体直接套用。旧版部署说明见项目中的 `MODEL_DEPLOY.md`；以实际启动模式及服务端协议为准。
