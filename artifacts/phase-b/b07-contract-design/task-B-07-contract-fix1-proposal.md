## 2. I1: physical locator identity and complete usage occurrences

`SourceGraph={locatorRows:[FullRow(source_locator)],sourceUsages:[SourceUsage]}`. locatorRows contains exactly one row per referenced locator ID and only the existing dictionary columns; it has no global role, version or source hash. Equal typed locator identity may be reused by several origins. FullRow/UUID/numeric/null/string/codec conventions remain old §§1,4,5.
```text
SourceUsage = {usage:UsageKey,locatorId:Uuid,origin:Origin,
               role:MEETING|BACKGROUND,sourceVersion:SourceVersion,sourceContentHash:Hash}
UsageKey = {kind:"EVIDENCE",evidenceId:Uuid}
 | {kind:"DETECTION",detectionId:Uuid,locatorId:Uuid}
 | {kind:"BACKGROUND",noteId:Uuid,locatorId:Uuid}
 | {kind:"EXCLUSION",exclusionRevisionId:Uuid,locatorId:Uuid,category:SensitiveKind}
Origin = {kind:"GENERATION_INPUT",inputId:Uuid,inputFingerprint:Hash}
 | {kind:"TRANSCRIPT_CONFIRMATION",confirmationId:Uuid,revisionId:Uuid,contentHash:Hash}
 | {kind:"APPLIED_INPUT",inputId:Uuid,inputFingerprint:Hash}
```
Each alternative has exactly the listed keys; sourceVersion has the exact old §5 union keys. No optional omitted members. UsageKey identifies a stored membership/occurrence independently of origin. Repeated UsageKey rejects even when byte-equal; different origins for the same UsageKey also reject. Distinct UsageKeys must survive even if locator/origin/content are identical. locatorId repeated inside a key must equal outer locatorId and the corresponding row FK.
Ordering: locatorRows by canonical lowercase UUID unsigned UTF8 bytes. sourceUsages by kind rank EVIDENCE=0, DETECTION=1, BACKGROUND=2, EXCLUSION=3, then the alternative's non-kind fields in their displayed order, lexicographically; UUID/category compare unsigned UTF8 bytes. These are set projections: sort after duplicate validation, independent of supplied collection order. Other row lists retain old dictionary-PK tuple ordering. No digest, display collation or sourceVersion controls occurrence identity/order.
Exact expected UsageKeys are derived from included stored rows: EVIDENCE for each included evidence_link.id; DETECTION for every included sensitive_detection_source PK; BACKGROUND for every included background_note_source PK; EXCLUSION for every included sensitive_exclusion PK. action_suggestion has no independent locator membership and creates no extra usage; it can prove an ACTION evidence origin under §3.
Require bijection between expected keys and supplied/derived sourceUsages, and equality between locatorRows IDs and union of usage locatorIds. Reject missing/extra rows, dangling references, duplicate keys, mismatched meeting/target/set/revision/category and conflicting physical locator rows. Include empty lists explicitly; never silently drop an unsupported occurrence or merge memberships. Pure checks validate this equality against complete detached row facts; later S2 owns authoritative query completeness/ACL.
Role, sourceVersion and sourceContentHash are derived independently for each usage via §3; they are checked against that exact origin's fixed source projection. Never allow a caller to choose one of several contexts merely by supplying a desired version. Alias s1 etc remains local to its original single input fingerprint; historical usages are keyed by persisted membership, not by a cross-input alias.
I1 example: N1.input_id=G1 and N2.input_id=G2, both joining L=PDF_PAGE(F,1), produce one locatorRows[L] and two usages BACKGROUND(N1,L)/BACKGROUND(N2,L). The first binds G1/D1/P1/hash1; the second G2/D2/P2/hash2. Neither conflicts merely because L is shared. Both source versions and hashes enter the encoded data; changing either changes its projection. This remains true with two sensitive labels and mixed directory origins.

## 3. I2: exact stored proof paths and unsupported histories

`StoredProvenanceFacts` supplies detached actual rows, exact archived config/profile artifacts and immutable file/parser content facts. It is not an asserted map from evidence IDs to arbitrary input IDs. S1 derives/verifies every step below, including all same-meeting references, unique membership, source bounds and matching content hashes. S2 later acquires authoritative complete facts; S1 cannot authenticate their storage origin or infer a missing edge.
|Usage/target|Only supported stored derivation|Origin and limit|
|---|---|---|
|BODY evidence|evidence_link.minutes_revision_id → minutes_revision.generation_input_id → exact generation_input and its fixed source catalog|GENERATION_INPUT. Evidence locator must belong to this exact input. Manual edit/restore must retain the edited/restored body's chain. Null input cannot be repaired from current state.|
|Detection membership|sensitive_detection_source.detection_id → sensitive_detection.input_id → generation_input|GENERATION_INPUT, retaining each copied detection's original input_id.|
|Background membership|background_note_source.note_id → background_note.input_id → generation_input|GENERATION_INPUT, retaining each copied note's original input_id.|
|ACTION evidence|evidence_link.element_id → minutes_element(category=ACTION) → action_suggestion(element_id).input_id → generation_input|GENERATION_INPUT. The existing action_suggestion row, not action_item or body input, is required for this route. All supplied local evidence must resolve within that fixed input.|
|Ordinary element, or ACTION without a usable suggestion chain, TRANSCRIPT evidence|evidence_link.locator_id → source_locator exact transcript_revision_id/segment_id → same revision's segment and unique transcript_confirmation(meeting_id,revision_id) → revision/batch/source file/processing input|TRANSCRIPT_CONFIRMATION. This is intrinsic confirmed-transcript identity, explicitly not a recovered original generation input. It supplies MEETING role and the old TRANSCRIPT SourceVersion.|
|Applied exclusion membership|sensitive_exclusion PK and selected exclusion_revision → exact final body's generation_input.exclusion_revision_id; locator must resolve in that input's fixed catalog|APPLIED_INPUT. This hashes the context in which the exclusion is applied, not an unrecorded detection-selection origin. Preserve both labels.|
All input-linked TRANSCRIPT usages must resolve the confirmation fixed by that input; no fallback to another revision. Intrinsic TRANSCRIPT requires exactly one stored confirmation for the exact revision and its complete saved segment/mark/source graph; no nearest/newest confirmation. A missing input chain for an input-linked body/directory usage does not silently switch it to intrinsic provenance.
For ACTION, if a present suggestion has an invalid/mismatched chain, reject rather than fall back; intrinsic fallback is only for an absent usable stored origin by design (e.g. no suggestion), not contradictory facts. The intrinsic route never claims a parser/material context. No ordinary non-ACTION local PDF/PPT/WORD/TEXT/AUDIO/KNOWLEDGE origin is reconstructable solely from its evidence/element/set rows under this profile: return PROVENANCE_UNAVAILABLE. The same restriction applies to an ACTION lacking its origin chain for nontranscript evidence.
There is no evidence_link.input_id/prior-evidence FK; minutes_element and element_set have no origin input/parent edge. generation_candidate.input_id only describes its own candidate target graph. A new adopted/copied target is not linked back by matching text/anchor/locator; generation_input.element_set_id identifies an input set, not every output element's origin. Body-only and element-only lifecycles stay separate. result_review.hash_profile and result_review_evidence do not supply a missing origin. These negative statements override any old implication of universal recovery after copying.
For a supported input-linked material path, derive the material revision through that input's material_snapshot membership and stable material reference/file relation, and resolve parser selection from that input's archived CATALOG/config dependency definition. Require exactly one parsed_document satisfying the pinned material revision and parser selection, its immutable text file/hash and exact parsed_unit membership. Two possible documents under the same selection are ambiguous; do not select by ID/order/created time/current parser. Distinct unambiguous selections P1/P2 across G1/G2 are allowed for the I1 graph. AUDIO additionally requires the archived capability's immutable real-duration/source-membership facts; absent defined capability fails.
Local parser origins for ordinary copied elements remain unsupported even when a caller supplies both historical candidates and one preferred origin, even when only one textual candidate appears to match. No latest configuration, current body input, candidate scan, text matching, raw JSON, audit text, file-reference kind or new column repairs this missing edge.
Fixed failures (extend old FailureCode): PROVENANCE_UNAVAILABLE for a required unrepresented/missing stored origin; SOURCE_CONTEXT_AMBIGUOUS for multiple eligible context/selection proofs; SOURCE_MEMBERSHIP_MISMATCH for missing/extra/duplicate/conflicting usage membership. Existing PROFILE_UNAVAILABLE covers missing archive/profile chain; CAPABILITY_UNAVAILABLE covers unimplemented archived capability. Validate profiles, stored paths, membership and bounds before producing any digest; return no partial success/hash on failure. Codes carry no source text or raw exception. If defects coexist, no ordering-dependent successful resolution is permitted; ambiguity is never resolved by collection order.

## 5. Recoverable hash-profile chains, including B06 alignment

The generation config's CONFIRMATION_HASH reference must agree with this owning chain; it cannot redefine an old confirmation. Never infer profile from digest length/content or currently installed code.
Manual text/mark/restore revisions inherit the concrete parent's processing_input_id, as the adopted transcript contract requires. A future deliberate confirmation-profile conversion requires a new immutable processing input/config dependency graph and explicit reviewed transition; never clear the existing chain or overwrite an old manifest. Missing/unsupported/conflicting archive data fails PROFILE_UNAVAILABLE. B06 must align to this chain and the old confirmation content projection before B07 wiring; S1 does not alter B06 or invent config_manifest contents in existing rows.
FINAL_SOURCES still resolves final_confirmation.minutes_revision_id → minutes_revision.generation_input_id → that input's fixed prompt/model config graph → FINAL_SOURCES and codec dependencies. Manual minutes edit/restore inherits the edited/restored input chain; nullable legacy/pure-handwritten body input has no recoverable final profile and fails PROFILE_UNAVAILABLE. Do not backfill from latest. Review rows independently pin their existing hash_profile. These profile chains determine encoding rules, while §3 separately determines source provenance; one never substitutes for the other.
