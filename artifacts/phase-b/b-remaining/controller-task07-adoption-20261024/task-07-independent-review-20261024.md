## Important findings

### T7IR-01 — A stale pending receipt permanently consumes local Worker/reconciler capacity

**Important.** Primary location: `backend/worker/src/main/java/ama/worker/ExternalExecutionSession.java:70–78`. Supporting locations: same file `:23–26,43–45,64–66`; `backend/worker/src/main/java/ama/worker/ReconciliationLoop.java:55–65,90–98`; `backend/worker/src/main/java/ama/worker/WorkerLoop.java:125–129,232–235`; `backend/adapters/src/main/java/ama/task/JdbcExternalOperations.java:228–246`.

A session keeps `pending` when observation returns STALE_TOKEN, makes receipt-only sticky, and retries that identical receipt with the same immutable-in-practice token. Sticky receipt-only also disables renewal. Neither retry nor the pending loop obtains fresh operation authority. `reconcilePrepared` retains the semaphore slot for pending sessions; subsequent polls retry them first and can call `claimReconciliation` only after acquiring a free slot. Therefore a capacity-1 prepared reconciler whose ACTIVE-owner token expires before a terminal receipt is observed has no reachable same-instance recovery path: every retry is correctly STALE_TOKEN, the slot never releases, and the fresh claim needed to recover is never made. At larger capacity, enough such receipts produce the same saturation.

This is not merely conservative global model-permit debt. Permit maintenance still runs, but it cannot make a nonterminal execution terminal or free this local semaphore. A separate reconciler completing the execution does not necessarily repair the old Worker slot either: takeover changes epoch/owner, and terminal replay requires the old token's epoch/owner to match before acknowledging. WorkerLoop uses the same pending/slot-retention pattern. Recovery then requires process replacement rather than the specified bounded same-fact/fresh-authority progression.

Reproducible branch sequence without changing business authority: use actual prepared ReconciliationLoop capacity 1; let it claim an execution for an ACTIVE owner; force a real operation renewal failure/expiry before returning the authoritative prepared receipt; let `observe` return STALE_TOKEN; poll repeatedly with DB healthy. There is no token assignment after initialization, no slot release and no further claim. Also cover old Worker receipt plus another reconciler's successful takeover/settlement, proving the old local slot eventually retires safely.

Required correction: provide bounded transition/transfer to fresh reconciliation authority or durable exact-result lookup while preserving the same receipt, no resend, sticky loss of the old context's business permission, and no premature global permit settlement. Do not weaken ACTIVE stale-token rules or simply acknowledge an unverified receipt. Add deterministic actual-DB tests showing both recovered fact and later unrelated work progress on the same capacity-1 instance.

The selected heartbeat-loss tests (`Task07ExternalWorkerIT.java:50–62`) force a local false renewal while the DB token is still live, so receipt-only immediately records STALE and never enters this failure. The selected saturation test verifies permit maintenance, not recovery of a stale pending receipt. Protocol §7 explicitly requires preserving the fact for a fresh reconciler/lookup; §9 requires pending-receipt recovery rather than a permanently stranded owner.

### T7IR-02 — Publication freeze is checked through an obsolete RR snapshot

**Important.** Primary location: `backend/adapters/src/main/java/ama/task/JdbcGenerationRetention.java:34`. Supporting locations: same file `:27–37`; `backend/adapters/src/main/java/ama/task/JdbcExternalOperations.java:195–203,264–272`; `backend/integration-tests/src/test/java/ama/task/Task07GenerationRetentionIT.java:35–43,108–116`.

`observeCurrent` performs nonlocking operation/execution/task discovery before acquiring identity/subject/meeting roots. Under the supported MySQL repeatable-read behavior this establishes a snapshot. Retention later reads meeting and subject with `FOR UPDATE`, so it sees the current greater revision, but checks READY/RUNNING/RECONCILING publication using a plain consistent SELECT. A publication transaction can commit its publication row/state under the same roots after the observation snapshot and before observation obtains those roots. The helper then sees the new business revision and `ever_published=0`, but the old publication snapshot. It issues retention and allows a STALE candidate to be written during the current publication freeze.

The same-root serialization does not cure an older consistent read. The existing controlled policy does not prelock publication at all; merely adding an earlier locking read in a future policy would also not turn this subsequent plain SELECT into a current read. Root fields remaining unchanged after retention is insufficient: the denied effect is the candidate write during an in-progress publication.

Required correction: make the publication-freeze decision from complete fresh/current domain facts acquired in the domain phase before tasks/operation/executions. Preserve the established lock order; do not discover a new publication root after external locks as a shortcut. Bind and consume the resulting authentic held facts or otherwise use the already-held current rows correctly. Add a deterministic RR barrier test: hold the publishing transaction's relevant roots, let observation complete its preliminary snapshot discovery, commit READY/RUNNING/RECONCILING publication (with a valid current root and `ever_published=0`), then release observation and assert no current/retention writer. The exact verified remote terminal fact must still follow the proper fenced path.

The passing `publicationFreezeDeniesRetention` inserts RUNNING publication before observation begins, which cannot expose this race. The root-race test advances only revision, with no publication. This violates adopted root ruling 4 and the helper's claimed fresh absence-of-publication predicate even though production Task 11 registration is correctly still absent.

### T7IR-03 — Prepared replay short-circuits verified success contradicting zero-effect failure

**Important.** Primary location: `backend/adapters/src/main/java/ama/task/JdbcExternalOperations.java:228–244`, especially `:233`.

After a prepared execution records a verified FAILED_ZERO_EFFECT observation, its operation/execution remain current, FAILED, and retain the same epoch/owner. A later independently verified SUCCEEDED observation for that exact execution enters the new terminal-replay branch at line 228. `same` is necessarily false because the stored state is FAILED, so line 233 returns STALE_TOKEN before the preserved contradiction block can set MANUAL_REQUIRED/CONTRADICTORY_SUCCESS and emit EXTERNAL_CONTRADICTION. This happens before `verifyReplay`, so a policy's default-deny replay implementation cannot repair it.

The inherited legacy path reaches lines 239–244 for the identical proof contradiction. A contradiction arriving only after a newer execution has been created also reaches that block because the replay branch requires current execution equality. Thus existing legacy old-generation tests do not cover the newly broken prepared/current-failed case.

Impact is stronger than a missed replay acknowledgment: the operation stays FAILED with its zero-effect proof even after a verified success was supplied, leaving `retryAfterZeroEffect` eligible to append a new execution for an effect now known to have happened. That defeats the quarantine/no-duplicate-effect safety boundary.

Required correction: preserve contradiction handling before terminal replay/conflict rejection for authoritative SUCCEEDED versus an exact execution with verified zero-effect FAILED proof; retain full original-spec/execution verification and no domain writer. Test the prepared path both before and after a successor execution exists, asserting QUARANTINED, MANUAL_REQUIRED, one contradiction event, no output/current effect/new send, retry denial after quarantine, and no settlement of a newer reservation. Also retain genuine equal-terminal replay and unequal success-result rejection tests. Protocol §7 explicitly orders proof contradiction before replay, and T7-G2 requires preserving the matrix.
