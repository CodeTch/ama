# B04 managed backend identity proposal — root decision required

No SQL or storage algorithm change. New managed-boundary codec uses only JDK SHA-256, DataOutputStream and strict UTF-8. The input is a counted list of non-null strings, each encoded as a four-byte unsigned big-endian byte length followed by exact UTF-8 bytes. Unpaired surrogates, missing fields and noncanonical locations fail closed. Domain/version is the first field. The 32 digest bytes become exactly 64 lowercase hexadecimal ASCII characters, the managed backend ID. ID itself is never a digest input. Every definition construction and historical session/file lookup recomputes it before routing. The numeric config_revision is an explicit operational configuration revision; it cannot authorize a different physical definition for the same ID.

S3 fields, in order: `ama-managed-s3-v1`, canonical endpoint origin, region, data bucket, control bucket, pathStyle as `true|false`, keyBudget in canonical decimal, and `layout-v3-199-200-8`. These are the reviewed S3Config.physicalBinding fields except backendId. Endpoint normalization admits only the already supported origin (no userinfo/path/query/fragment), lowercase scheme/DNS host and explicit effective port; IPv6 uses canonical URI representation. Reject noncanonical input rather than silently reinterpret paths. Credentials, timeout, admission, chunk size, object/native budgets and retry settings are excluded because they do not change object placement. A changed endpoint/bucket/layout/path-style/key-budget derives a new ID. Old definitions remain registered for history; no fallback to the default backend.

Local fields, in order: `ama-managed-local-v1`, canonical HTTPS service origin (stable VIP/DNS and effective port), logical volume ID, canonical POSIX root relative to its configured mountpoint, filesystem type, and `local-layout-v1`. The relative path includes every component and rejects `..`, duplicate slash and symlink-derived aliases. Root equal to mountpoint has one explicit representation `.`. The service configuration computes the relative path from its actual protected `root` and `mountpoint`, not a caller-provided duplicate. Existing MountedVolumeGuard still checks actual kernel mount/device/source, `.volume-id`, inode/root and active-role facts on every operation. Physical device major/minor, source-device spelling, absolute mountpoint, node bind address, role-file path/current active instance and PKI material are deliberately excluded so the same logical replicated volume, relative data root and stable service origin can switch nodes without a new backend ID. Changing the relative root or logical volume identity changes the ID. Rotating certificates/credentials does not.

`FileServiceMain` receives a protected `serviceOrigin` for managed IDs. If backendId is exactly 64 lowercase hex, it must derive and match the ID from actual root/mountpoint/volumeId/filesystem/serviceOrigin before store/server creation. This managed-ID detection has no bypass flag. Existing arbitrary opaque IDs remain supported only by the independently reviewed storage port/infrastructure composition; the B04 managed catalog rejects all such IDs. Thus removing managed settings cannot make a same-ID service start, and changing server root cannot evade the API definition. TLS continues to authenticate the service origin; no new PKI identity format is invented.

Production configuration is an explicit immutable map of these complete definitions plus separately reloadable credential/TLS suppliers. Readiness checks only configured adapters and records their actual revision/status in storage_backend. Disabled/READ_ONLY policy is explicit; empty configuration yields unavailable storage, not ready. Controlled test composition will use derived IDs too; the existing infrastructure-only tests need no rewrite. Golden codec values, endpoint/bucket/root remapping rejection across fresh processes, credential/timeout rotation retaining IDs, original-backend routing after default change, and a protected FileServiceMain root-mismatch startup rejection will be exercised.

Limit: copying a logical volume marker and full data root onto unrelated media while also forging the protected mount/role configuration is outside application configuration identity; MountedVolumeGuard and the HA/fencing qualification own that threat. This proposal does not claim two-node takeover, volume authenticity, power-loss durability or company endpoint qualification. A legitimate physical relocation with a new logical identity requires a new backend ID and separately reviewed migration, never remapping existing records.
