### Important (Should Fix)

1. **Multi-model configuration can shrink capacity below committed in-flight reservations.** `backend/adapters/src/main/java/ama/task/JdbcModelPermitPool.java:19–36`, especially the nonlocking `inflight()` count at line36 and its use at line30.

   `configure()` explicitly rejects ambient transactions with `independent()` and opens its own `q.tx.required` transaction. The unchanged `backend/adapters/src/main/java/ama/db/TransactionRunner.java:14–24` does not set an isolation override; `MysqlDataSources.java:23–31` likewise does not force READ COMMITTED. Therefore the supported/default MySQL REPEATABLE READ path remains relevant. The INSERT/locking SELECT of each model does not create a consistent-read snapshot, but the first plain `SELECT COUNT(*)` in `inflight()` does. That snapshot persists across the remaining model iterations.

   Concrete interleaving: models A and B both have older configuration revisions; B has capacity2 and one unsettled NULL-deadline reservation. Configuration locks A and counts A, establishing its ReadView. Before it reaches B, a concurrent valid B admission obtains the B lock and commits a second reservation. Configuration then obtains B's current row lock but its plain count still sees only the original reservation, so a new B capacity1 revision is accepted with two in-flight calls. Sorted model locking prevents one deadlock class but does not refresh the reservation view. This violates the shrink-floor requirement in `docs/superpowers/specs/2026-10-21-ama-database-design.md:146`.

   Fix by materializing/prelocking the complete sorted model set before the first consistent reservation read, or by another explicitly current-read strategy that preserves the model/reservation order. Do not introduce ambient/domain/operation locks into configuration. Add a deterministic real-MySQL REPEATABLE READ interleaving test pausing after A's count, admitting B, and asserting the B shrink is rejected with prior configuration intact. Existing `ModelPermitIT.java:12,14` tests single-model shrink and concurrent initial configuration separately; neither exercises this ReadView case.

2. **An authoritative contradictory success can be silently discarded while waiting for the subject lock.** `backend/adapters/src/main/java/ama/task/JdbcExternalOperations.java:81–97`, particularly lines83,89 and92.

   `observe()` reads the operation and the token's execution without locks, then waits for subject/domain/task locks. After locking the current operation/execution it still decides whether a success contradicts zero-effect proof using the pre-lock `old` execution object. For example, a current reconciler holds the subject and records definitive zero-effect failure while an old sender's success observer has already read that execution as MARKED. After the reconciler commits, the success observer obtains the locks and sees the locked execution/operation as FAILED, so `valid()` is false; however `old.state()` is still MARKED and line92 rejects the contradiction branch. It returns STALE_TOKEN and leaves FAILED retryable instead of entering MANUAL_REQUIRED. This stale Java object issue also exists under READ COMMITTED, not only REPEATABLE READ.

   There is a related early discard at line89: if a verified retry advances `current_execution_no` between candidate discovery and the operation lock, the method returns STALE_TOKEN before examining a late success against the old execution's zero-effect proof. Both windows violate the explicit contradictory-success rule in `docs/superpowers/specs/2026-10-21-ama-database-design.md:128,138`; an allowed future retry can proceed despite the success evidence this API was supposed to quarantine.

   Revalidate the token execution/proof with current locked reads after the required subject→all relevant tasks→operation→executions order. If the generation changed and additional task locks are needed, restart discovery/transaction safely instead of acquiring those tasks after the operation lock or dropping the observation. Add deterministic real-MySQL tests for both zero-effect commit and retry-generation advancement while a success observer waits. Existing `ExternalExecutionIT.java:40` checks a sequential late contradiction after retry, which does not cover either interleaving. Keep stale-token domain callbacks fenced; the fix is to retain/quarantine the verified external fact, not restore old write authority.
