# Recording protocol v1

The browser opens one recording session and receives a `sessionId`, `partId`, `writerEpoch`, and fixed `backendId`. A stream chunk carries `partId`, `writerEpoch`, `seq` (starting at 1), `sampleStart` (starting at 0), `sampleCount`, and a SHA-256 digest of the PCM payload.

The server persists the binary chunk and its manifest before returning an ACK. `highestContiguousSeq` only advances across persisted sequences; `missingSeqs` lists absent sequence numbers below the highest received sequence. A duplicate sequence with the same digest and identical sample range is idempotent. A duplicate sequence with a different digest, an old writer epoch, or a session that has finished is rejected.

`finish` includes the final sequence for every part. The server creates an archive task only after every sequence from 1 through each final sequence is present. Temporary chunks remain available until the archive verifies the merged output.

V034 retains explicit historical database PCM; new production chunks use immutable local file storage with a committed MySQL manifest (V036). A new process reads session, pause/finish state and committed chunk proofs from MySQL. An outer transaction rollback cannot leave process-local ACK state behind. Legacy rows without PCM fail closed and are not reconstructed. Chunks are PCM16 mono at 16 kHz, at most 64,000 bytes (two seconds), and must match sampleCount exactly. Issued part identity and adjacent sample continuity are checked; the retry window is bounded to 512 sequences.

Paused device reopening uses `POST /recordings/{id}/parts` with `X-Expected-Epoch`. It issues a new part and increments writerEpoch; old writers and writes to sealed parts fail. Each part restarts seq at 1 and sampleStart at 0. Up to 16 parts are retained in issued order; finish must declare every part (0 for an empty issued part), with at least one nonempty part. V039 adds database writer leases and the standard Spring WebSocket binding described below. The HTTP finish response alone is not proof of a playable archive.

New deployed chunks use the session's managed FileBackendCatalog identity and immutable `recordings/<sessionId>/<partId>/<seq>` logical keys. The FileStoragePort put must confirm exact bytes/hash before the manifest transaction commits. A caller rollback preserves the immutable file for the original retry; different contents for that key conflict. V036 distinguishes new file keys from explicit historical database PCM. Reads do not fall back from a missing file route to another backend. The server bounds a complete session to 4096 chunks, 16 parts and 115200000 samples (two hours).

Archive preparation requires a finished session and independently verifies each issued part's contiguous seq/sample ranges and every chunk's actual length/SHA256. It streams through private bounded scratch storage into canonical PCM16 mono 16kHz WAV, preserves part-to-archive sample ranges, and puts an immutable archive at `recordings/<sessionId>/archive-v1/<inputFingerprint>`. Scratch data is never exposed as an available archive. The v1 input fingerprint is SHA256 of big-endian length-prefixed UTF-8 version/session/backend, int32 part count, each ordered part ID and int32 chunk count, then each chunk's int64 seq/start/count and length-prefixed SHA256. A verified immutable archive blob remains preparation evidence until durable task completion and file-reference registration succeed.

V037/V038 install `RECORDING_ARCHIVE_V1` in the existing durable queue and an explicit bounded local worker pool. Finish seals capture, then independently admits an immutable task input; it returns `{sessionId, finalSequence, archiveTaskId}` only after admission commits. Admission failure preserves the sealed PCM and original finish may be retried. Active and successful admission replays retain the task, including after meeting metadata changes. After a terminal failure, an explicit finish/archive request creates a new generation and retains the old failed task history; it never resurrects the old lease. Per-meeting task/attempt history bounds still apply.

`GET /recordings/{id}/archive` returns `{taskId,state,available,sampleCount}`. `POST` on that path requests admission/retry under current owner EDIT authorization. Task navigation uses `GET /meetings/{meetingId}/recording-archives/{inputId}`, with the same current READ authorization and exact persisted input relation. A prepared artifact remains unavailable. Only the queue's actual validated WRITING invocation can transfer the upload's protective reference to `RECORDING_ARCHIVE`; READY, the file ledger and task success commit atomically. A failed success event rolls all three back. A normal registry owner gate cannot register a PREPARED archive outside this invocation.

`GET /recordings/{id}/audio` streams registered `audio/wav` under fresh current meeting READ authorization. It supports one `Range` header, 206/Content-Range and 416. The file registry verifies the exact current archive/input, original recording backend, size/hash/purpose and actual successful task output, with task acquisition after the complete file set. A missing, unregistered or superseded artifact has no playback route. Grant revocation/deletion is enforced for each new read. No physical file locator is returned. Archive preparation/registration does not delete acknowledged technical chunks.


V039 adds a database-clock writer lease. `POST /recordings/{id}/writer-lease` accepts bounded JSON `{expectedEpoch,collectorId,requestId}`; a successful claim advances the epoch and returns the original session/backend/current part plus `expiresAt`. Exact active claim replay is idempotent. A different collector cannot replace a live lease. `POST .../writer-lease/renew` accepts `{expectedEpoch,collectorId}`, preserves the epoch and extends the lease by 30 seconds. Client IDs do not authorize access: every call still resolves the current HTTP identity and holds current owner EDIT, meeting mutation and recording row gates. Confirmed/final or ever-published meetings deny new capture. Reads and already-sealed finish replay remain separately authorized.

Chunk requests include `X-Collector-Id` and `X-Writer-Epoch`; pause, resume and new-part use `X-Collector-Id` and `X-Expected-Epoch`. New part atomically clears the prior connection binding and advances the epoch. A new lease preserves the current part for exact cached retransmission; reopening a device starts a new part only after all pending original bytes have been confirmed. Unfinished finish requires the lease; a sealed identical finish can replay without a capture lease. Control JSON is limited to 1024 bytes, rejects duplicate/unknown fields and trailing content, and finish declares at most 16 UUID part keys.

The same-origin `ws(s)://<application>/api/v1/recordings/{sessionId}/stream` endpoint uses the browser cookie, exact Origin and two offered protocols: `ama.recording.v1` and `ama.csrf.<current-in-memory-CSRF>`. It negotiates only `ama.recording.v1`; no identity token or CSRF appears in the URL. A bounded HELLO `{type:"HELLO",collectorId,writerEpoch}` must arrive within five seconds. READY is scoped by session/part/epoch. Every binary message freshly resolves the current identity and current meeting/freeze/lease/connection gates; opening a socket does not grant continuing authority. An old socket close cannot release another epoch or connection.

Binary messages contain an 80-byte big-endian header followed by little-endian PCM16. Offsets are magic ASCII `AMA1` at 0, part UUID bytes at 4, int64 epoch at 20, int64 seq at 28, int64 sampleStart at 36, uint32 sampleCount at 44, 32 SHA-256 bytes at 48, and PCM at 80. The maximum frame is 64080 bytes. ACK adds `{type:"ACK",sessionId,partId,writerEpoch}` to the HTTP ACK fields. Transport errors, timeout, close and temporary/stable transcript text never imply durable saving. Client uploads are serialized and accept only an exactly scoped, bounded ACK.

HTTP and WebSocket share one bounded actor/session/collector token bucket and a global ingress budget, evaluated only after authorization. Epoch changes do not reset this budget. Rejections return HTTP 429 with Retry-After or socket 1013/RATE_LIMITED without advancing the manifest. Native frame/control limits and a finite connection cap apply independently. These resource counters carry no authorization or durable ACK authority.

The browser retains immutable unconfirmed chunks and exact per-chunk successful-upload receipts. A high contiguous ACK does not prove that an unsent local chunk has the same content; cleanup removes only exact bytes already confirmed by this uploader. An actor-scoped IndexedDB transaction records the chunk, capture cursor and pending-byte budget together. Removing confirmed bytes leaves the capture cursor and final part manifest intact. Cache exhaustion aborts the transaction and prevents further unbounded capture. Browser microphone, interruption and native UI qualification are recorded separately from synthetic PCM protocol qualification.


V040 adds one admission row per meeting. Repeating or racing create returns the same active session, preserving its backend and part; this prevents independent session IDs from bypassing the per-meeting collector fence. A completed historical session remains intact when the next session is admitted. A pre-existing single active session is adopted; multiple historical active identities fail closed without choosing one or rewriting evidence.

`GET /recordings/{id}/manifest` holds the current owner read gate and returns `{sessionId,paused,finished,parts}` in issued order. Each part contains `partId,highestContiguousSeq,highestReceivedSeq,sampleCount`. Persisted out-of-order sample totals do not imply a contiguous timeline. A browser adopting server state refuses an unresolved gap and retains the old part cursor; it cannot erase cached PCM from these metadata facts alone. New device capture starts in a newly issued part after exact pending retransmission.

The application owns one native AudioWorklet pipeline across route changes. The worklet averages channels, sends one bounded block at a time, waits for local-persistence credit, and stops explicitly if its finite ring overflows. A stateful resampler converts the actual device rate to canonical little-endian PCM16 mono16kHz, with 32000-sample chunks and a bounded final tail. Pause drains the device tail and confirms its saved bytes before pausing server input. A failed local write retains its exact bounded chunk in the current page; recovery first uploads old cached chunks to free quota, then retries the retained chunk. Device reopening creates a new part; browser shutdown/sleep is never advertised as continuous capture. Legacy MediaRecorder files stay separately downloadable.


Every writer claim, renewal, connection bind and frame guard now locks the meeting admission before its session row. A single unambiguous historical active session can be adopted. Ambiguous historical active sessions cannot establish independent writers, and a known old session outside the current admission cannot bypass the fence. Its original PCM and read/recovery evidence remain intact. V041 indexes the bounded historical lookup; discovery under the already locked admission takes no cross-meeting range lock. The close-only cleanup still compares the exact session/epoch/collector/connection and never grants capture authority.

Client renewal responses are scoped to their original session, part, epoch and collector. A late refusal from an old part cannot stop the new device or overwrite its renewal timer. The new part establishes its own renewal cadence. A lost finish response is recovered by reading the current sealed manifest and replaying the exact finish only when every local part/sample range matches and no cached or in-memory unconfirmed samples remain; this metadata path cannot erase pending audio. The server's sealed finish/admission remains the only completion authority.

For long file-backed archives the internal local adapter may read the exact frozen chunk manifest through one bounded `read-sequence-v1` response. Every original chunk length/hash, part order and final EOF remains checked. Legacy database PCM or a resumed mixed session follows its original persisted route. Transport batching never grants business access, changes the accepted backend, removes ACKed chunks, or publishes an archive before the existing producer transaction succeeds.
