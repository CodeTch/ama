## Findings

### T5SR01 — Important: batch deadline and known lease loss do not reach reads inside source open

**Primary final location:** `backend/adapters/src/main/java/ama/task/TranscriptImportRuntime.java:90` (registration and remaining-batch watchdog at lines 91–92).

`components.sources().open(...)` runs before either the execution's abort registration or its batch-lifetime wrapper exists. The `cancelled` supplier created at lines 64–65 is not passed through this call. This is observable for the real LOCAL path: `LocalFileClient.send` wraps the response but consumes a non-2xx error body at `backend/adapters/src/main/java/ama/storage/LocalFileClient.java:79` before returning. Its timer only knows `bodyLifetime`; the production constructor uses five minutes, and the request timeout is also five minutes. The actual production mapping reaches that constructor through `ManagedBackendAdapters.local`.

For a task with a one-second (or the demonstrated sixty-second) batch deadline, a LOCAL 503 response that sends a byte and stalls keeps the worker inside `open` until the separate transport timeout. The batch deadline does not abort it. If the actual renewal fails during this window, `Execution.renew` sets sticky loss but has no registered abort action, so that known loss likewise cannot release this reader promptly. The S3 open path also performs binding/control-body reads and HEAD before it returns the data stream; those operations have only their individual transport limits. This is a resource-lifetime/cancellation defect, not a claim that expired work can write RAW: the later cancellation/final DB checks still deny completion.

The original design sections 3, 6 and 9 and R1 sections 2.3/5 require whole-batch bounds and known-loss/close source cancellation across open/body work. A finite per-response transport timeout is useful and implemented, but does not implement the independently configured batch deadline or cancel this earlier reader. Existing evidence does not close this composition window: `Task05TransportIT:30` uses an explicit 350ms standalone client; `Task05CancellationIT:24` registers only after `client.read` has returned and stalls the successful body afterward.

**Required fix:** establish the deny-only execution cancellation/deadline at the source/transport boundary before request/metadata/error/control-body work begins, preserving the genuine source-authorization protocol and commit-before-I/O rule. Each in-progress transport must be cancellable under the remaining batch bound, with exactly-once release and no new reader thread left behind. Do not merely lower all global transport timeouts or change the lease/authority protocol.

**Focused proof:** with a genuine registered import and owned real LOCAL TLS route, set a short batch bound and a much longer transport bound, send a 503 header plus a partial body, and keep the fixture stalled. Show actual preparation/reader exit and release before fixture release at the batch bound. Repeat with a real renewal loss while the error body is being consumed. Add the analogous pre-return S3 control/open boundary if that shared path is changed. These are proposed probes, not tests executed by this reviewer.

### T5SR02 — Important: one failed abort permanently skips the rest of Worker shutdown

**Primary final location:** `backend/worker/src/main/java/ama/worker/WorkerLoop.java:207`.

`close()` sets the global closed flag, stops scanners, and then calls `executions.forEach(Execution::cancel)` before shutting down heartbeats/workers. `Execution.cancel` at line 132 directly invokes the registered abort with no exception isolation. If one abort throws, iteration and `close()` stop immediately: remaining sources are not signalled, heartbeat and worker executors are not shut down, and the bounded join is never reached. A second close returns at line 205 because the flag is already true, so it cannot finish the skipped cleanup.

This is a reachable exceptional transport path, not only an arbitrary hostile callback. `TranscriptImportRuntime.java:91` catches `IOException` only, while `RangeReader.close` invokes `S3Objects.release`; `backend/adapters/src/main/java/ama/storage/s3/S3Objects.java:105` converts a failed body close into an unchecked storage-unavailable exception. The new generic contextual API also permits an abort action to fail. A backend close failure must deny success, but cannot abandon the other owned execution resources.

The same exception propagates through `backend/worker/src/main/java/ama/worker/TranscriptWorkerRuntimeProvider.java:40`: runtime `closed` is set before `loop.close()`, and definitions are only closed afterward, so the owned backend cleanup is skipped and also cannot be retried. This violates the adopted bounded shutdown/resource ownership/error-path contract.

**Required fix:** make cancellation best-effort across every execution, always shut down/join owned executors and always attempt backend close in finally-style cleanup. Preserve the first error or a bounded aggregate after cleanup, preserve interruption, and make repeated close safe even after a partial failure. Abort callbacks must remain outside the execution monitor.

**Focused proof:** run two active contextual preparations, make the first registered close/abort throw and the second record its cancellation, then close. Assert the second action still runs, no post-close writer/quarantine occurs, every executor reaches its required bounded termination, and backend close is attempted once despite the first error. Also cover repeated close after the failed first cleanup. No suite rerun was performed here.
