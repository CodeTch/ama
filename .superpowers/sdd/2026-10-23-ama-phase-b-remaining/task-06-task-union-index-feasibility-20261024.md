## 3. Same-subject narrowing changes the selected graph

Let `I` be every durable task with the selected typed input, `S` the tasks under the selected meeting subject, and `P` the actual RAW producer PK. Current candidate membership is `I ∪ {P}`; a collection restricted to the same subject plus actual producer is `(I ∩ S) ∪ {P}`. These sets differ whenever an additional task references the same input from another subject and is not `P`.

For example, keep the valid producer and add a second task under another subject with the same `TRANSCRIPTION_INPUT` ID. This is a source-level counterexample, not an executed fixture: the current candidate and `TranscriptReadGraph` observe two rows and fail the exact-one check. A same-subject collection omits the second row and can pass that check. Retaining the actual producer PK still detects a malformed producer itself; it does not detect additional cross-subject references. V010's typed input fields and subject FK do not constrain every task's input ownership to its subject; the inspected 13-script schema contains no such invariant. A producer-key uniqueness constraint limits equal producer keys, not every row referring to one input.

Therefore same-subject restriction is **not a semantics-preserving repair of the present complete input-task union**. The adopted R1 calls for complete relevant facts/full declared union, and supplies no explicit exemption for cross-subject same-input references. Its PK/unique-key discovery rule does not itself prove those references absent. Ordinary valid production may emit only the correct subject; that does not prove equivalent behavior on the extra/corrupt graph cases this completeness check is intended to reject.

The smallest unresolved contract is a source/schema-backed way to enumerate and protect the **complete typed-input task membership (including unexpected cross-subject rows) plus actual producer PK** through indexed bounded discovery and held recheck, consistent with declared-set/rank rules. Alternatively, excluding those rows would require an explicit changed completeness definition/invariant and its authority; none is established by the inspected inputs. This note supplies neither a new index/DDL/query design nor permission to narrow semantics. Root's independent metadata/EXPLAIN check remains necessary to characterize actual behavior.

## 4. Root-supplied subject-index proposal: semantic and capacity costs

After the initial source check, root supplied a concrete proposal: enumerate the complete current subject with an ID-only nonlocking query ordered by `created_at,id`, using `maxTasks+1` under the genuine subject/meeting root; union the actual producer PK; acquire UUID-sorted task locks and then filter to the relevant typed input. This paragraph describes root's message, not a newly inspected implementation or a design supplied by this note.

The proposal's **discovery domain is all tasks of the subject**, whereas its final relevant collection remains the narrower same-subject input set plus producer discussed in section 3. The actual producer remains included even if malformed under another subject, but additional foreign-subject tasks referring to the same input are still excluded. It therefore changes the current candidate/readers' anomaly-detection semantics. Under the unchanged adopted requirements it cannot be characterized as merely equivalent index selection. The exact normative tension is preserved R1 line 89, “Full declared RAW producer task union,” and line 92, “Pure facts include complete relevant FullRows, ContentFiles and StoredTasks,” together with “Task discovery uses declared PKs/unique producer key, not scanning all tasks by unindexed input_id.” The first two do not expressly define a same-subject exemption; the existing readers make the complete input union concrete. R1 line 117 further requires bounded predeclared sets and no late expansion. Whether to authorize a narrower graph is a recorded root contract ruling, not an inference justified by the presence of `task_subject_history`.

The capacity cost is independent of foreign-subject semantics. With a 64-task complete-subject admission limit, 65 tasks under the selected subject can cause failure even when only one task is relevant to the selected input. Tasks for different inputs, task types, states, and accumulated history all consume that discovery allowance if the proposed collection truly covers the entire subject. The former global input union counts relevant input tasks plus the producer, so this new failure condition is observable behavior; no bound increase is assumed or proposed here. Locking all discovered subject IDs before filtering also acquires unrelated same-subject task locks. If the producer PK is outside the enumerated subject, accounting for that additional ID within the existing task/row/edge budgets must be explicit; the supplied prose alone does not establish it.

A genuine held subject/root can protect its compliant writers' subject set; it does not establish complete global membership for another subject. Nonlocking ID discovery plus later UUID ordering is therefore not by itself a proof that foreign-subject references cannot exist or change. This is the smallest missing scope/invariant contract identified above, separate from the indexed lookup question. No broader writer audit or locking proof was performed.
