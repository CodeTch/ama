## Required forward schema discrimination

A durable discriminator is required before production v1 batch creation coexists with unlabelled historical batch hashes. Recommended minimal forward schema: new sidecar `input_batch_fingerprint_profile` with `batch_id` canonical UUID PK/FK to `input_batch(id)` and `profile` exact ASCII code, initially only `ama.input-batch.v1`. Insert in the same transaction as every new B06 batch. Treat missing sidecar as legacy/unknown; never infer v1 from hash shape, creation date, membership, current default, or a passing recomputation. No mass backfill and no rewrite of existing hashes. Historical B06.2 controlled receipts remain historical metadata evidence, not a production backfill source.

A nullable `input_batch.fingerprint_profile` column is a viable alternative, but the sidecar avoids changing adopted fixed `MinutesContracts.Table.INPUT_BATCH` / FullRow shape and old rowset/canonical fixtures. Read the sidecar as separate domain facts; keep exact existing v1 byte encoding. No need for a second batch hash implementation or for a manifest version bump just to discriminate the batch hash. Unknown versions fail closed for operations requiring batch verification; existing historical diagnostic reads may return an explicit unsupported-profile status without mutating anything.

Root must assign the actual next forward migration only after reviewing repository migration history and other pending schema work. This preflight assigns no migration number and includes no executable DDL. Required migration checks: old rows untouched, new profile FK/uniqueness/allowed values, mixed-history fail-closed selection, rollback of a failed new-batch transaction. A processing-pointer or saved flag is not required for the recommended model. Correction schema is conditional on the readiness decision below, not smuggled into this migration.

Important lock constraint: no raw files, archive traversal, strict JSON parsing, whole-body hashing or parser work inside the final write transaction. First obtain bounded detached facts; build/hash the proposed batch/manifest outside; then fresh gate/CAS and exact equality recheck. It is legitimate for the final transaction to insert its own new batch and use a capability authenticating those actual uncommitted rows. It is not legitimate to claim `readBatch` saw those rows or mint a held token from detached DTOs. A forged/expired/foreign-source/foreign-holder/wrong-batch capability must fail.

Do not implement worker file access by generalizing `/files/{id}/content` to accept any old input/reference. A worker lease DTO is forgeable: verify actual durable_task state/spec/attempt/owner/DB expiry and current subject under the ordered locks before returning a pinned read receipt. File/session checks precede task locks; queue completion independently rechecks after parsing. Source I/O stays outside those locks. D06 periodic stream revocation remains separate.

## Intake, task identity, and currentness

1. Require ordered unique nonempty fileIds, EMPTY materials (null snapshot normalized explicitly), configured strict TXT parser and finite deployment budgets. Metadata/name/category absence does not block. Do not guess a parser from extension or MIME; unsupported parser/format is an explicit capability error.
2. Read authoritative draft facts and exact archived processing closure. Allocate batch/input IDs and target fence. Recommend intake itself advances meeting revision and subject business version once, leaving cancellation epoch unchanged; manifest/base and TaskSpec use that exact post-intake fence. CAS requires the previously read fence. This avoids inventing a current-input column and makes a newer intake invalidate older work. The prior saved transcript stays readable until an explicit new save; current confirmation/final pointer invalidation for changed processing intent must be specified consistently with needs_generation.
3. Compute `BatchFingerprint` v1 and canonical IMPORT/TXT/EMPTY manifest using actual file IDs/order/hash/size and exact config references outside transaction. No own stored input/task/output placeholders.
4. Final transaction follows idempotency → complete identity → subject/meeting → complete domain set → original sessions → files → tasks → audit/events → one final flush. Idempotency request digest contains actual browser semantic request, excluding generated IDs. Matching completed replay reauthorizes and returns stored safe taskId; changed request conflicts; no new task/file bind.
5. Insert new batch/profile/members/input under fresh held proof, prelock all reference owners, one `bindAll` with exact original UUID and expected locationRevision. Validate original purpose through the controlled provider, COMPLETED, same meeting, original key/size/hash, AVAILABLE, route and epoch. Remove only that precise protective UPLOAD_SESSION reference. Adopt B03 gate into the production task policy and enqueue the full immutable spec in the same transaction. Any failure restores all references/rows/fences.

Proposed exact production task contract (new technical contract to review, distinct from all TEST keys): type `IMPORT_TXT`, configured pool `TRANSCRIPT`, subject `MEETING:meetingId`, input `TRANSCRIPTION_INPUT:inputId`, fingerprint equal to persisted processing fingerprint, businessVersion/cancelEpoch equal to manifest base, explicit priority and maxAttempts from controlled policy. Initial producer key is SHA-256 using the existing canonical codec over envelope `{profile:"ama.transcript-producer.v1",kind:"TASK_PRODUCER",data:{operation:"IMPORT_TXT",meetingId,inputId,inputFingerprint}}`. Object field sorting/string encoding is the adopted codec's, with independent golden vector tests. No string concatenation, hashCode, test-domain key, random key per queue retry, or filename hashing. All complete TaskSpec fields are compared on collision. An explicit user retry needs a new stable retry-operation identity in a separately versioned key grammar and preserves old input/task; do not pretend ordinary lease retry creates a new logical producer.

Production policy validation must check type/pool/producer key and original-purpose contract itself: S1 currently validates input/fence consistency but does not require IMPORT_TXT type or production producer grammar. To keep canonical work outside locks, carry prevalidated immutable projections and compare the exact held rows/spec; task policy may validate bounded structural fields. A constructor-visible DTO or `effectsAllowed=true` is not authority.

Purpose proposal: explicit controlled local code `TRANSCRIPT_INPUT` in upload capability and first-reference policy, never the test `CONTROLLED_INPUT`. Validate original persisted session purpose; do not add invented input_batch_file.purpose or infer purpose from request label. Exposing capability requires a configured valid backend and actual installed provider; unknown purposes stay unavailable. Server derives exact original UUID from completed_file_id and rejects zero/multiple matches; optional browser upload UUID, if accepted, must equal it and cannot override it.

## Worker, saved state, marks, confirmation

Recommended B06 authority model: IMPORT output is immutable RAW and is not an explicit human save. Task output typed reference is `TRANSCRIPT_REVISION:rawRevisionId`, with exact batch/input/fingerprint/actual producer_task_id; segments preserve parser stable IDs/paragraphs and null time/speaker. Owner can inspect RAW. The first PUT creates WORKING, parent RAW, and advances current saved pointer. Later saves create WORKING children. Member effective reads use the current saved WORKING (or an explicitly adopted later saved kind), never any latest row or RAW/candidate existence. This satisfies explicit-save/unsaved-confirmation requirements without adding a saved boolean. If root chooses import-as-saved instead, it must explicitly settle how original unsaved-confirmation tests and the browser's unsaved editor state are represented; do not infer saved from producer NULL or kind alone without a contract.

Parse every file in ordinal order after archive/input verification and authentic source acquisition. Aggregate finite file/count/decoded-text/segment budgets across the whole batch; per-file limits alone are insufficient. Retain raw source and metadata; close every stream. Parser failure/lease loss must not leave partial revisions or segments. Prepared result allocates output IDs and immutable segment data outside transaction; completion inserts RAW and segments and returns typed output atomically with task result. No success before commit. Stale current fence means no output effects; do not widen queue stale-token acceptance to save a late candidate. Rich late-candidate retention requires its own expressly reviewed seam.

Save validates expected meeting revision and exact parent/source provenance, creates a new revision, copies unchanged segments/marks, and applies complete submitted mark sets. Existing segment sourceFileId/sourceParagraph and nullable TXT time/speaker are server-authoritative; arbitrary client source relabeling or new fabricated stable IDs fail. Blank final content cannot confirm. Inherit original processing_input_id/batch/input_fingerprint; human output producer_task_id is null while the parent/import producer chain stays recoverable. Every content/mark save clears current transcript_confirmation_id and final_confirmation_id, advances meeting/subject, and sets needs_generation. RAW and historical saved rows remain immutable. Restoring history creates a new WORKING with that history's fixed processing chain, not the current default chain.

Confirmation: read complete actual saved graph and archived closure outside the final write transaction, compute via the additive draft hash path, then reacquire authentic current EDIT and exact saved pointer/fence and equality-check all relevant immutable facts before inserting confirmation/updating pointer. Require nonempty content, complete valid sources, complete marks, saved status and authoritative zero-PENDING correction state. Current saved identity + exact content hash are canonical; browser flags are ignored. `(meeting_id,revision_id)` uniqueness returns the same confirmation for repeated unchanged confirmation; replay cannot reconfirm an obsolete saved revision or enqueue generation twice. A confirmation may append a single confirmed event; B07 generation remains its explicitly registered workflow and must receive only actual current confirmation facts. No dummy generation task in B06.

No correction table exists in current applied source. Recommended minimum is a `CorrectionReadiness` port with an explicit supported deployment mode proving correction producers are disabled/not installed, yielding the empty correction domain only for that controlled mode. Unknown/enabled-without-reader fails unavailable. When corrections are installed, the provider must query their complete current persisted state under the existing meeting fence. Never implement `return 0` as if it queried a table. If the acceptance contract requires exercising real PENDING rows now, root must coordinate an additional forward correction schema/provider from the approved C03 design; this adds a schema/review slice and cannot be represented as a passed B06 check. Record which qualification is actually delivered.

Historical metadata/transcript reads retain original manifest and fences and never substitute current values. Owner EDIT history endpoints can inspect exact historical saved/RAW/candidate versions; member routes return permitted effective saved versions only (publication later fixes the final graph). Historical file-byte access must require an explicit authorized version path and registered proof. Existing B04 original-epoch checks remain intact unless separately reviewed; stored historical transcript visibility does not automatically grant arbitrary old upload bytes or revive cancelled uploads.
