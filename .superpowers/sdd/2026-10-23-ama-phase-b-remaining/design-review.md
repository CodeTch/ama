## Findings and exact bounded refinements

### DR-01 — Important: editor-epoch equality cannot prove absence of editing, and original epoch equality blocks intentional adoption

**References:** spec lines 12, 15, 19; plan lines 14, 22; adopted UX `docs/superpowers/specs/2026-10-22-ama-minutes-ux-decisions.md`, first-save and concurrency rules.

An editor can acknowledge an intent, start typing, then begin generation. Capturing its positive epoch and only suppressing autosave when the epoch subsequently advances treats that existing editor as absent. Conversely, requiring explicit adoption to match the original editor epoch makes a correctly retained candidate permanently unadoptable after a new intent. Neither behavior follows the approved rules.

**Accepted coordinator ruling, to put in the spec:** create an actual guard at epoch 0 only in the same transaction as a new meeting. Missing guard on legacy meetings is UNKNOWN and never authorizes first autosave. Every first edit-capable transition acknowledges a fresh authenticated owner command before typing/paste/restore/autosave is enabled. Under the meeting/guard lock, a missing legacy guard becomes 1 and an existing guard increments. Positive values permanently suppress first automatic save for that meeting; no reset, expiry, editor-close decrement or client assertion. The intent command does not advance businessVersion or cancelEpoch. Saturation/overflow fails closed; it cannot wrap to zero. Replay with the same actor/key/semantic request returns the committed result without incrementing again, but reauthorizes.

Automatic first save holds the same meeting root and requires a real zero guard, no effective body, original current business/input/cancel fence and current owner/lifecycle authority. Explicit adoption is a separate owner-confirmed CAS and input/provenance check; it **does not require the original editor epoch to remain zero/equal**. It does not silently rebase a business-stale candidate. The old body or typed draft remains intact on conflicts.

**Required evidence:** intent before generation, intent during generation, two owner windows, unknown guard, lost intent ACK/replay, refresh/restored draft, abandoned editor, explicit adoption after suppression, concurrent completion versus intent, and rollover rejection. Sticky suppression is conservative and consistent with the disclosed manual-adoption cost. It does not require another user product decision.

### DR-02 — Important: stale retention lacks an executable state/authority contract and a final-readiness race rule

**References:** spec line 15; plan lines 19, 22–23; B07/B08 preflight section C; `V012__minutes_evidence.sql:71` (candidate state/unique task); `JdbcExternalOperations.java:138–145` (ordinary canApply and fenced completion).

The prohibition on pointer/subject changes is good, but fresh identity alone does not specify the permission and authentic execution authority needed for a DB write. The draft also leaves retained results PENDING versus STALE unresolved. A late retained PENDING row after final confirmation could change readiness without advancing the subject or clearing the final pointer, contradicting the otherwise strict snapshot protocol.

**Bounded contract:** retain only through a registered generation-specific policy with private issuer/same DataSource/holder/purpose capability, complete prelocked graph, actual immutable task/input/producer, and exact current external execution/observation authority. Recheck current ACTIVE owner EDIT authority and valid meeting lifecycle, same cancellation epoch, no published/governed/deleting state. A task/receipt DTO, old owner flag, or generic effects callback cannot mint this capability. The sole relaxed predicate is the original businessVersion equality for this immutable result-retention operation; generic enqueue/claim/renew/send/ordinary completion remain strict. Receipt recording without business authority remains the existing B05 fact-only path.

Freeze disposition explicitly: a result whose original business fence no longer matches is retained as STALE with its original input, task, base_revision and fingerprint. It is owner-private, non-adoptable under that stale original fence and nonblocking as a pending candidate; owner can inspect/dispose/regenerate. No current pointer, needs_generation, confirmation, or subject mutation occurs in retention. A result at the current business/input fence suppressed only by editor intent is PENDING and can be explicitly adopted or rejected with fresh CAS. PENDING rows block final readiness; STALE rows do not erase other blockers such as generation debt or changed current input. Existing-body regeneration remains PENDING until adoption/rejection if its fence is still current.

The prelocked final/review/publication path must serialize against candidate dispositions on the same meeting root. Define exact task result/terminal representation for retained candidate versus fact-only receipt; do not let UI infer adoption from task SUCCEEDED. A retained output can be discoverable separately even where the task is recorded fenced. Avoid inventing new terminal enums without a reviewed forward contract.

**Required evidence:** final-confirmation versus late retention, input/metadata edit versus result, intent-only PENDING adoption, stale candidate reject/regenerate, deletion/revocation/publish/cancel fail closed, old operation tokens, cross-holder capabilities, duplicate observation uniqueness, and full rollback. The detailed Task 7 protocol is an explicit activation gate; Task 1 need not implement it.

### DR-03 — Important: external completion ownership must hand off heartbeat authority, not merely suppress a second complete call

**References:** spec lines 14, 20; plan line 19; actual `JdbcExternalOperations.java:30–50,77–79,94–145`; `ExternalOperationPort.java:10–22`; B07/B08 preflight sections B and B05 limits.

`beginExternal` changes durable_task to RECONCILING and creates operation-token authority before network. A handler left under ordinary task renewal is expected to lose the RUNNING task lease check; carrying the ordinary lost flag into observation would discard or quarantine a real external result even though its operation token remains valid. Merely returning an externally-owned marker to avoid queue.complete does not solve this cross-mode race.

**Bounded contract:** Task 7 owns an explicit state machine: ordinary task lease before marker; committed operation marker/token and model permit; atomic handoff from task heartbeat to operation/reconciliation heartbeat; network; token-bound prepared observation; exactly one completion owner. A committed marker with uncertain worker ACK must be rediscovered and queried, never resent. No ordinary queue completion or ordinary failure quarantine after handoff. Operation heartbeat loss suppresses domain application but does not erase authoritative fact receipt. Revoked identity, expired task lease and authoritative late success must still use existing fact-only/quarantine semantics without regaining business permission. Retain/retry the same observation on preparation/rediscovery failure, never another external send. Specify close/interruption behavior and which heartbeat scheduler owns each phase; do not introduce a competing lease provider.

**Required evidence:** task renew tick immediately after beginExternal, concurrent handoff/tick, app death after marker before network and after remote success before observe, operation lease expiration/reclaim, revoked owner with authoritative receipt, no second complete, and permit settlement only from verified terminal facts. This is a Task 7 gate, not a reason to expand Task 1.

### DR-04 — Important: v2 saved-graph operations and final review obligations need explicit closure

**References:** spec line 19; plan lines 21–23; adopted minutes contract lines 16–18; `StoredSourceGraph.java:26–83`; `ResultHashProfiles.java:108–159`; `ReviewCoverageEvaluator.java:9–34`; `V012__minutes_evidence.sql:13–18,39–59,108–134,150–180`; normative proposal sections 110–113; data dictionary result_review/result_review_evidence.

The spec promises editing, adoption, human review and finalization with the old v2 graph, while leaving the supported operation matrix and the required-review set implicit. S1 can validate the supplied selected reviews and still accept an empty final review membership; it intentionally does not decide which business claims need review. V012 has no general persisted element/evidence source_context. D01 v3 solves a broader problem and cannot be inferred merely because materials happen to be empty.

**Bounded contract to freeze before Tasks 9–11:**

| Operation | Required v2 behavior |
| --- | --- |
| Candidate generation and first/explicit adoption | Persist complete immutable candidate body/set/elements/evidence/directories/suggestions. Adopt via new saved graph/target identities with complete owner-ID remapping and preserved input/source relations, or an explicitly reviewed equivalent that leaves candidate history immutable. No copied review credit. |
| Body save | New minutes_revision inherits exact generation_input/profile chain; preserve/reanchor the complete body evidence for the new text with valid scalar anchors. No latest input substitution or invented provenance. Element set remains fixed unless the same command explicitly versions it. |
| Element/action-field edit | New immutable set/affected targets and complete copied children; retain supported transcript/input relations, remap action_suggestion and directory joins, preserve original suggestion separately from accepted action_item. Old target/source reviews grant no new credit. |
| CONCLUSION/ACTION to OPEN_QUESTION | Explicit saved semantic conversion preserving source/history. ACTION-only rows must not remain attached to a non-ACTION target; retain old suggestion in immutable old history, not by violating the new category graph. The API must actually support this approved insufficiency path. |
| Source change or restore | Allow only transformations whose full original context is unambiguously reconstructable by adopted v2 chains. General mixed-source/body/ACTION rebinding, unsupported copies and v3 basis/material histories fail with a capability error before any write; they remain required D01/D03/D04 work. |

Complete facts must enumerate accepted fields, suggestions, all body/element evidence, source locators, background and sensitive rows and their complete joins, applied exclusions, inherited original inputs/tasks/archives, reviews and membership. Empty categories/collections remain explicit; do not fabricate NOT_EXTRACTED rows. Reject omitted/extra/cross-meeting rows and unsupported original chains with cumulative bounds.

Define final required-review selection independently of hashing: each current CONCLUSION/ACTION requires the current exact whole-target SOURCE_SUPPORT=SUPPORTED review with complete nonempty relevant evidence and MEETING support; every current ACTION additionally requires exact ACTION_FIELDS=CONFIRMED for the actual accepted tuple, including explicit nullable values. Any additional required body scope must be deterministic and exposed by readiness, not inferred by a hash helper or by model confidence. Never demand source support for all OPEN_QUESTION items merely to make a blanket rule easy. No partial-scope union, arbitrary older SUPPORTED, empty evidence support, adoption-generated support or generic-final-click attestation. Review writes advance root/subject and clear final pointer, as the adopted contract states. Final snapshots freeze the exact selected IDs under the meeting root; historical reconstruction uses them, not latest reviews. Draft final hashing must use an explicit prospective entry and compare the same algorithm, never a placeholder stored-success hash.

**Required evidence:** actual generate→saved/adopted graph→action acceptance→exact source review→final across fresh JVM; body edits and category conversion; directory/suggestion remapping; omitted evidence and stale/partial/empty reviews; subsequent review does not change historical final; unsupported v3 histories fail atomically. This refinement does not require implementing all D01 now or deleting later requirements.

### DR-05 — Important: browser CAS must not round int64 versions, including existing info/roster writes

**References:** spec line 21; plan lines 16,18,22–24; B09 preflight item 10; `contracts/openapi/meetings.yaml:175–179,187–196,241–243`; generated TypeScript numeric revisions.

The current integer contract allows values beyond JavaScript Number.MAX_SAFE_INTEGER. Implementing the remaining browser flow with generated number values can send the wrong CAS revision. Solving only newly added transcript/minutes commands leaves the existing information/roster steps broken at the same meeting revision.

**Bounded compatible wire refinement:** add canonical decimal revisionToken/accessRevisionToken (and token forms for other externally used counters) to new server read projections. Canonical spelling is zero or nonzero decimal digits with no sign, whitespace, leading zeros, exponent, decimal point or floating conversion; parse/range-check against the existing server-supported integer domain. Browser retains tokens as opaque strings and never derives them from the numeric fields. Add an optional expectedRevisionToken alternative to every browser-used mutation, including existing info and roster commands; legacy exact JSON integer requests remain accepted. If both are present they must represent the same exact integer, otherwise reject; choose and document one normalization before idempotency digesting. New browser requests send token only. Do not cap real DB revisions at 2^53 or narrow a historical contract silently.

**Required evidence:** 9007199254740991/2/3 and the current highest supported value round-trip through real HTTP + browser request generation; stale conflicts retain drafts; malformed tokens and unequal dual forms reject; semantically identical dual/legacy/token normalization has the documented replay behavior. Generated schemas/typecheck/API checks are necessary, not sufficient for this boundary.

### DR-06 — Important: missing authoritative read/discovery contracts must be explicit task outputs before UI integration

**References:** spec line 21; plan lines 16,18,21–24; complete B09 preflight backend-freeze items 1–10; original B09 refresh/task-resume requirement.

Task 12's general projection wording does not allocate all reads needed to make the promised loop reloadable. Without these contracts, an implementation can pass known-ID mutation demos but require browser memory for uploads/tasks/candidates/publications, or infer owner privileges from roster/admin role. This is a functional and access-control design omission rather than a request for company documentation.

**Bounded output checklist to add to producer tasks and plan table:** authorized owned/joined meeting list and workspace-resume projection; explicit viewer capabilities/lifecycle/read-only reason; server-discovered upload session/accepted receipt/completed-file state and frozen ordered input association; task status and typed output discovery with bounded polling or resumable event cursor; current/owner-history/member-effective transcript/body reads; owner-private candidate comparison/disposition/eligibility; authorized source preview + review history/readiness; current final and publication discovery; allowed controlled dictionary and library/folder selection. Each endpoint has actor/meeting ACL, no-store/private appropriate responses, bounded payload/pagination, safe error and replay contract; internal keys/routes/credentials never appear. Server must distinguish a completed upload from an eligible business source, task success from adoption, and publication UNKNOWN from retryable failure.

Freeze exact paths/shapes/generated types before each consuming UI slice; Task 4 can own upload/input discovery, Task 6 transcript/history, Task 9/10 minutes/candidate/reviews, Task 11 final/publication/destination, Task 12 list/workspace/session composition. Define folder root semantics from the controlled provider's actual returned IDs; no invented sentinel offered as a company protocol. Same-origin HTTPS test topology must exercise actual Secure HttpOnly session/CSRF/Origin and four separate identities. Local/S3 runs use actual controllers/storage/workers/DB, not route.fulfill business success. Tests must reopen from server IDs after process restart and after lost accepted responses.

## Accepted design decisions and remaining nonblocking proof gates

1. **Profile sidecar:** approve the choice in principle. A one-to-one batch FK/PK with exact profile code preserves adopted FullRow/hash shape; insert atomically for every new batch. Missing/unknown historical rows fail verification, without time/hash/shape inference or backfill. Read it as separate authentic domain facts; do not change old rowset bytes or auto-relabel old fixtures. Need independent sidecar DDL/data/rollback tests before runtime activation.
2. **Forward stage patch:** compatible in principle with the migration register's coordinator-owned stage-patch rule (`docs/database/migration-register.md:23,165–167`). No new integer is allocated here; V014–V027 owners stay reserved and the next new integer remains V028. Do not leap to V028 merely for these B sidecars and then require outOfOrder for later C/D. Root must prove the chosen patch ordering with pinned Flyway and the exact permitted fixture high-watermark before allocation/freeze/ACK. Higher or failed/unknown histories are excluded and require a separately reviewed forward path. Existing twelve formal scripts remain byte-identical. This review grants no SQL execution permission.
3. **RAW/WORKING and correction boundary:** explicit saved WORKING after owner-inspectable RAW is coherent with original unsaved-confirmation tests. Complete marks and inherited processing provenance are mandatory. An actual disabled/not-installed correction capability is honest for B; unknown/enabled-without-reader fails unavailable. No claim that a real C03 PENDING correction row was tested.
4. **Import contract:** spec's TRANSCRIPT_IMPORT_V1/TRANSCRIPT_IMPORT and canonical producer profile explicitly supersede preflight alternative names; this is a technical identifier choice, not a company protocol. Compare the full immutable spec on collision. Authentic upload purpose/session/route and current/owner/worker contexts remain mandatory.
5. **Atomic ordinary completion:** DB-only callback before actual output validation, all effects/terminal state/audit/outbox in one rollback boundary, preserves the supplied preflight defect analysis. A Supplier remains composition, not authority. Task 1's separate review/test gate is appropriate; this design review makes no code correctness claim.
6. **Fairness and external qualification:** the >64 held/unregistered-candidate follow-up remains open until bounded cross-call progress is implemented and independently evidenced. No external worker activation before closure. UNKNOWN and generic not-found never authorize resend. Controlled durable HTTP protocols qualify local mechanics only; no company endpoint/proof format is invented.
7. **Phase boundary:** original B permits EMPTY materials and TXT first flow; C owns media/corrections, D owns broader material/provenance/partial-edit/governance work. Finishing the enumerated controlled B operations is compatible with approved architecture. Do not call arbitrary TXT editing or full source rebinding supported merely because materials are EMPTY. Company SSO/directory/model/KB, production HA/fencing/native I/O/capacity remain separate; preserve B01 IMM PARTIAL and B04 Q401 UNKNOWN.
