## Important residual: T7IR-01 — pending zero-effect receipt cannot retire after explicit retry advances the execution

**Affected fix:** `backend/adapters/src/main/java/ama/task/JdbcExternalOperations.java:241-257`, especially the current-execution requirements at 241 and 255; `backend/worker/src/main/java/ama/worker/ExternalExecutionSession.java:70-78`.

**Requirement:** Fix01 brief line 11 requires bounded recovery/retirement of stale receipts while preserving the exact durable fact, no resend, sticky authority loss, and no premature global permit release. The original T7IR-01 requires the same-instance local capacity to become usable again. The adopted protocol permits explicit retry only after authoritative zero-effect failure; such a retry is part of the existing state machine, not an invented malformed state.

The fix correctly handles a later owner of the **same current execution**, but current execution equality prevents recovery of an already committed **older** terminal receipt. The following permitted sequence is sufficient:

1. A prepared Worker session observes an authentic `FAILED_ZERO_EFFECT` receipt with complete proof. The DB transaction commits the external execution as FAILED, ends its exact task attempt, and records the task result. The commit acknowledgement is lost before `ExternalExecutionSession` clears its pending receipt. The existing after-commit hook pattern in this suite can produce this exact window.
2. While that session still retains the same receipt, an authorized explicit `retryAfterZeroEffect` request is accepted. `JdbcExternalOperations.java:319-328` checks the definitive failure/proof, fixed input and current domain, inserts the successor execution as PREPARED, and advances `current_execution_no` while setting the operation to RETRY_QUEUED. **The successor need not start**; no second local worker slot is required to enqueue this retry.
3. The old session retries its original receipt. Discovery already loads and locks both old and current tasks/executions (`JdbcExternalOperations.java:201-226`), and the original registered policy can verify that receipt. Nevertheless, terminal replay at 241 requires `o.execution()==token.executionNo()`. The requirement fails because the operation now points at the successor. The success-vs-zero-effect contradiction branch does not apply: the receipt being retried is the same zero-effect failure, not contradictory success.
4. The ordinary observation returns STALE_TOKEN; the session sets `receiptOnly=true`, `recoverReceipt=true` and retains pending at `ExternalExecutionSession.java:71-72`. Its subsequent `recoverPreparedFact` calls also return STALE_TOKEN at `JdbcExternalOperations.java:255`, because the same current-execution equality is required. They never reach a replay verifier for the old stored result. A completed successor does not restore equality either.
5. The pending receipt therefore remains indefinitely. `WorkerLoop.java:125-129,235-236` releases the local semaphore only after pending clears, and `ReconciliationLoop.java:55-58,93-97` has the analogous rule. With capacity one, unrelated work—and potentially the queued successor on that Worker—cannot proceed in the same instance.

This is an **Important liveness/capacity correctness failure**, not a Critical integrity loss. It is a remaining boundary of the new recovery implementation and the exact original IR01 requirement. I do not count it again as a separate new finding.

**Global permit debt is different:** settlement recovery runs before reconciliation capacity checks (`ReconciliationLoop.java:55-57`) and may correctly settle the old terminal execution's model reservation. That does not clear `ExternalExecutionSession.pending`, release its local slot, or make its old operation token current. No recommendation here permits releasing a still-nonterminal reservation, releasing a successor's reservation, or treating a timeout as proof of zero effect.

**Why the supplied passing tests do not close this:** `Task07ReceiptRecoveryIT.java:44-65` covers expiry plus recovery and later-owner success on the same execution; `:67-78` covers live-owner/UNKNOWN/foreign-execution refusal and recovery-commit acknowledgement loss for same-execution success. All four cases use the success receipt for their positive recovery path. The routing fixture explicitly does not implement retry at `:29`. No case advances to a successor between old terminal commit and old acknowledgement. The modified prepared fixture's `verifyReplay` at `Task07PreparedExternalIT.java:100` recognizes success, invalid-output and stale-success results, but does not provide a positive exact zero-effect terminal replay verifier. A new failure replay test must give the registered test policy that legitimate verification behavior, rather than fail solely due to a default-deny fixture. The production current-execution gates reject the scenario before such a verifier could help.

**Required correction boundary:** Provide bounded acknowledgement/retirement of a verified exact old terminal receipt using that old execution's immutable proof, full original task spec, stored local result, and its exact ended attempt. Keep ordinary ACTIVE stale-token rules intact. For this zero-effect path, the old execution still carries complete immutable proof even though the operation's mutable summary now describes the successor. Verify the actual old stored result with the genuine registered policy and authentic holder/context; do not accidentally pass the successor's task result to old-receipt verification. Do not infer acknowledgement merely from the task being terminal or from `current_execution_no` being larger. Do not confer call authority, renew/reuse the old context for writes, rerun the writer, resend, mutate the successor's epoch/owner/state/output, or settle its reservation. The existing verified-success contradiction precedence must remain intact. This states required behavior and safety predicates, not a mandated implementation design.

**Required deterministic evidence (not run by this reviewer):**

- Add an actual-DB case with an authentic prepared FAILED_ZERO_EFFECT receipt and a registered verifier that accepts only its exact stored terminal result/proof. Inject acknowledgement loss after the old observation commits. Assert old execution/proof, old task result, and old exact `task_attempt` outcome/error/ended_at before accepting an explicit retry. Then enqueue the legitimate successor, leaving it PREPARED/RETRY_QUEUED, and retry the old receipt through the session path. Verify finite acknowledgement/retirement without a second output, event, attempt termination or execution.
- Exercise that sequence through an actual capacity-one Worker (and the shared prepared reconciliation capacity path, or an equally direct proof of that path). Poll with a bounded completion condition; assert the original local slot retires and unrelated work or the intended successor progresses in the same instance. This must not be satisfied by restarting/closing the loop, modifying its semaphore, or using another instance to hide retained local capacity.
- Add the successor-started variant: independently claim/begin the authorized successor and reserve its real model permit before old-receipt recovery. Assert successor token epoch/owner/state and unfinished attempt remain unchanged, its reservation remains unsettled, and only the old terminal execution's reservation can settle. Assert no original resend/call authority/writer invocation. Use enough configured global capacity or first settle the old terminal debt to make this legitimate setup possible; do not fake reservation rows.
